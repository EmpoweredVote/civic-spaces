# Phase 17-03 — Resolving a place with no account, and the rule that narrows

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn a typed place name — and, when ev-accounts ships the endpoint, a typed street
address — into the four or five geoids a civic space is keyed on, holding nothing but those
geoids and never showing the input back. Then edit the two places that still say this app
never geocodes, so the next reader does not treat the new code as a mistake.

**Architecture:** One pure module and one tiny stateful one, plus two thin React Query
hooks. `src/lib/placeResolve.ts` has no runtime imports, so the check runs the shipped
functions: it validates input, derives geoids from a `location-search` row, derives the
state from the county by FIPS construction, and parses both API responses. `src/lib/
viewedPlace.ts` is the only thing that touches `sessionStorage`, and it stores **geoids
only**. The address path is written in full and gated behind `VITE_PLACE_RESOLVE_URL`, so
when ev-accounts lands `POST /api/civic-spaces/resolve` the cutover is one environment
variable — the pattern `VITE_SLICE_ASSIGNMENT_URL` already set. No UI in this plan.

**Tech Stack:** TypeScript 5.7 · TanStack Query · Node 24 `--experimental-strip-types` ·
`public/geo/` (committed, offline, keyless) · no new packages (see `17-SHARED.md`).

**Spec:** `17-RESEARCH.md` **Q1 in full** — Q1.1 (no CORS, proven in a real browser), Q1.3
(every failure is a `200`), Q1.5 (the four candidate endpoints and why three are rejected),
Q1.6 (the path that works today), Q1.7 (the ask), Q1.8 (D-13 stated honestly) — plus
**Pattern 4**, **Pitfalls 6, 7 and 10**, and Security V5/V7/V13. `17-CONTEXT.md` D-12, D-13,
D-14, D-16, D-17.

## 🔴 The three endpoints that are rejected, and why — name them or someone will use them

The research probed all four candidates live on 2026-10-26, from
`Origin: https://civicspaces.empowered.vote`. Three are rejected. Write the reasons into the
module header, because each one is attractive and each one is wrong.

| Rejected | Why |
|---|---|
| `GET /api/essentials/address-search?address=…` | **Two D-13 violations.** The address is in the **query string**, which Render's access log records as part of the request line, and `matchedAddress` is **echoed back** in the response (verified: `"67 HAYWOOD ST, ASHEVILLE, NC, 28801"`). It is also missing the place geoid outside ev-accounts' `PLACE_LOADED_STATES`. It is the convenient option and it is the one to name as rejected |
| Browser `fetch()` to `geocoding.geo.census.gov` | **No CORS.** Reproduced in real Chromium from the real origin: *"blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present."* `vary: Origin` is present **without** `access-control-allow-origin`, and the `OPTIONS` 200 is an Apache `Allow:` response, which a browser reads as a failed preflight. 🔴 **Pitfall 7: Node's `fetch` does not enforce CORS, so every Node probe of this passes and the browser still fails.** Any future claim that it works must be made in Chromium from the real origin |
| JSONP (`format=jsonp&callback=`) to the same host | It *does* work (442 ms, verified). It also executes third-party script in this app's origin, reproduces only the **first** geocoder with none of ev-accounts' NAD and county-locator fallbacks — so "a real address returns zero matches" becomes a user-visible failure — and still puts the address in a query string. Documented fallback of last resort, **not** the plan of record. If it ever ships it needs a comment naming the missing header and the day it was checked |

The accepted answer is the one that already exists next door: a **body-only POST**, which
Render's access log does not record, copied line-for-line from
`essentialsCoordinateLookup.ts`. Task 6 is the ask.

- [ ] **Step 2: The shapes**

```ts
/** One row from GET /api/essentials/location-search. Every field optional: remote data. */
export interface PlaceSearchRow {
  geo_id?: string
  mtfcc?: string
  label?: string
  state?: string
  area_type?: string
  has_local_data?: boolean
}

/** The answer. GEOIDS ONLY — never the typed string, never matchedAddress. */
export interface ResolvedPlace {
  /** null for an unincorporated address or a county-level choice. An ANSWER, not a failure. */
  city: string | null
  county: string | null
  state: string
  /** Literals in ev-accounts' SLICE_ASSIGNMENTS — not looked up, never fetched. */
  nation: 'US'
  unified: 'UNIFIED'
}
```

🔴 **No `name`, no `label`, no `matchedAddress` field, and that is structural.** D-13 says
never echo the input back. The display name is resolved **from the geoid** by
`geoNames.ts`'s `lookupGeoName`, which is committed, offline and drift-guarded — the same
path `useJurisdictionName` already uses for a member's own slices. Making the name
unrepresentable here means no call site can accidentally render the input. Say so in the
doc comment.

🔴 `federal` and `unified` are literals. Research Q3.2: `SLICE_ASSIGNMENTS` keys federal on
`'US'` and `assignUnifiedIfNotAssigned` on `'UNIFIED'`. No lookup, and `volunteer` is
role-gated and never a visitor's.

- [ ] **Step 3: `normalisePlaceQuery` — ASVS V5, at the edge**

Trim; collapse internal whitespace; reject control characters; cap at 120 characters; return
`null` below 3 characters so the typeahead does not fire on one letter. No HTML is ever
constructed from it and PostgREST is not in this path, so there is nothing to escape — but
the cap and the trim are what stop a paste of an entire document reaching the API.

- [ ] **Step 4: `geoidsFromSearchRow` — branch on LENGTH, not on `mtfcc`**

```ts
export type SearchRowKind = 'place' | 'county' | 'state' | 'unusable'
export function searchRowKind(row: PlaceSearchRow): SearchRowKind
```

Rules, with the reasoning in the comment:

- 7 numeric digits → `place`. **Both `G4110` (incorporated place) and `G4120` (CDP) are
  places** and the research names both; branching on `mtfcc` would need that list kept in
  agreement with ev-accounts, where branching on length does not.
- 5 numeric digits → `county`.
- 2 numeric digits → `state`.
- anything else → `unusable`. **Not a throw.** Remote data from an origin we do not control
  is `toolCoverage.ts`'s stated model, and a row shape nobody anticipated must drop out of
  the list rather than take down a render.

Then:

```ts
/** state FIPS is the first two characters of a county or place geoid, always, by FIPS construction. */
export function stateFromGeoid(geoid: string): string | null
```

- [ ] **Step 5: `placeFromSearchRow` — what each kind can answer without a second request**

| Kind | city | county | state | Needs the centroid leg? |
|---|---|---|---|---|
| `place` | `geo_id` | **unknown** | `geo_id.slice(0,2)` | 🔴 **yes** — the gazetteer has no place→county link |
| `county` | `null` | `geo_id` | `geo_id.slice(0,2)` | no |
| `state` | `null` | `null` | `geo_id` | no |

Return a discriminated result — `{ complete: true, place }` or
`{ complete: false, partial, needsCounty: { geoid } }` — so the hook in Task 3 cannot forget
the second leg and the check in Task 4 can assert which rows need it.

- [ ] **Step 6: The two response parsers, and 🔴 Pitfall 6**

```ts
export function countyFromCoordinateLookup(body: unknown): string | null
export function placeFromResolveResponse(body: unknown): ResolvedPlace | null
```

Both read defensively and both return `null` rather than throwing.

🔴 **Never branch on HTTP status for the geocoder family.** Research Q1.3: the Census
Geocoder answers `200 OK` with `result.addressMatches: []` for every failure — a nonexistent
street, a PO box, a ZIP alone, a typo, **and a correctly-typed real address TIGER does not
carry** (`70 Court Plaza, Asheville NC` returns zero matches and is a real address). So a
parser that trusts `res.ok` reports "resolved" with every geoid `undefined`. Branch on the
*content*. The same discipline applies to `coordinate-lookup`: `locality.incorporated` is
`null` for Asheville because NC is not in ev-accounts' `PLACE_LOADED_STATES`, so read
`county.geoid` — which is nationwide — and nothing else.

- [ ] **Step 7: Typecheck and commit**

```bash
npm run build
git add src/lib/placeResolve.ts
git commit -m "feat(place): the pure half of resolving a place to its geoids

Import-free so check-place-resolve.mjs runs the shipped functions. ResolvedPlace carries
GEOIDS ONLY and has no name field at all: D-13 forbids echoing the input, and making the
name unrepresentable here means no call site can render it by accident — the display name
comes from the geoid through geoNames.ts, offline and drift-guarded. Rows branch on geoid
```

### Task 3: The two hooks

**Files:**
- Create: `src/hooks/usePlaceSearch.ts`, `src/hooks/usePlaceResolve.ts`

- Reference (do not edit): `src/lib/evApi.ts` (`EV_API_ORIGIN` — `''` in dev, so `/api/…`

- [ ] **Step 1: `usePlaceSearch(query)`**

`GET ${EV_API_ORIGIN}/api/essentials/location-search?q=<normalised>&limit=8`. Anonymous,
CORS-allowed, 136 ms / 622 B for five rows. `enabled` only when `normalisePlaceQuery`
returned non-null; debounce ~250 ms; `staleTime` a few minutes; `retry: 1`.

Map rows through `searchRowKind` and **drop `unusable` ones** before returning, so no
consumer has to.

- [ ] **Step 2: `usePlaceResolve()` — the place-name path**

A mutation (not a query — it is user-initiated and must not refetch): row → `complete`
answer, or → `POST ${EV_API_ORIGIN}/api/essentials/coordinate-lookup` with `{lat, lng}` from
`lookupGeoName(placeGeoid)` → `countyFromCoordinateLookup`.

🔴 **The centroid comes from the committed gazetteer, not from a request.** `lookupGeoName`
already returns `lat`/`lon` for the geoid and already shares one in-flight promise per state
shard. No new fetch, no key, and the 2.7 MB set is already shipped.

🔴 **One `coordinate-lookup` call per place change, never inside the typeahead.** The
response is ~100 KB (57 politician records with finance summaries and committee lists) and
measured at 1160 ms, bought for one 5-digit number. Acceptable once per chosen place;
indefensible per keystroke.

Failure is honest and final: if the place has no centroid in the gazetteer, or the lookup
returns no county, the result is "we could not work that place out" and the UI says so.
🔴 **Never a nearby county, never a state-level guess.** Treasury Tracker resolving an
unknown slug to Bloomington, IN's budget is the precedent — a real answer for the wrong
place is worse than no answer.

- [ ] **Step 3: The address path, complete and switched off**

```ts
const PLACE_RESOLVE_BASE = import.meta.env.VITE_PLACE_RESOLVE_URL ?? ''
export const PLACE_RESOLVE_ENABLED = PLACE_RESOLVE_BASE !== ''
```

`POST `${PLACE_RESOLVE_BASE}/resolve`` with a JSON **body** `{ address }` →
`placeFromResolveResponse`. Exactly the `${BASE}/assign` shape `sliceAssignment.ts` uses, so
the cutover is one variable.

🔴 **Its own variable, not `VITE_SLICE_ASSIGNMENT_URL`.** They point at the same engine base
today, which is exactly why sharing one is a trap: any deployment that has configured slice
assignment would silently switch the address path on and start 404ing against an endpoint
that does not exist yet. Two features, two switches.

🔴 **`PLACE_RESOLVE_ENABLED` is false by default and 17-04 renders no address input when it
is false.** No dead control, no copy promising a path that cannot run. Add the var to
`.env.example`, commented out, with one line saying it is set only once ev-accounts ships
`POST /api/civic-spaces/resolve` (and `/api/civic-spaces` in dev, so the Vite proxy handles
it).

🔴 **The error branch logs `(err as Error).message` and never the body.** ASVS V7 and D-13's
no-logging clause. `essentialsCoordinateLookup.ts` is the model on the server side; this is
the same rule on the client.

Contents, all of which the research already established:

- **The contract.** `POST /api/civic-spaces/resolve`, body `{ address: string }`, response
  `{ city: string|null, county: string|null, state: string|null, nation: "US" }` and nothing
  else. ~120 bytes.
- **The implementation, which is a copy.** `backend/src/routes/essentialsCoordinateLookup.ts`
  wholesale: `optionalAuth`, body-only transport with its privacy comment block intact,
  `express-rate-limit` 30/min/IP mirroring `coordinateLookupLimiter`, zero DB writes,
  `console.error((err as Error).message)` only. Then `geocodeAddress()` for the point —
  which brings the NAD and county-locator fallbacks with it — and the existing
  `G4110/G4120`, `G4020`, `G4000` `ST_Covers` queries in `essentialsService.ts` for the
  geoids, with a Census `geographies/coordinates` backstop for the states where place
  geofences are not loaded.
- **Why not the obvious alternatives.** The three rejections above, with the live evidence,
  so ev-accounts does not propose `address-search` back.
- **Why the fallback chain matters to the answer.** Q1.3: a correctly-typed real address can
  return zero Census matches. A client-side reimplementation reproduces the first geocoder
  and none of the fallbacks, so a user whose address TIGER does not carry would be told

- **Error codes this repo will render:** `PO_BOX_REJECTED` / `ADDRESS_NOT_FOUND` → 422,

  state and to the place-name escape hatch, never to a guess.
- **What unblocks:** one environment variable, `VITE_PLACE_RESOLVE_URL`, and the address

  must therefore say "geocoded once and never kept", never "never leaves your browser".
