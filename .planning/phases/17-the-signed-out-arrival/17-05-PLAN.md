# Phase 17-05 — The second entry point, the way back, and the check that watches both

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in member can go and look at another city from inside the app, and get
back. The same picker, in a second position, with one state behind both — and a committed
browser check that proves the place arrives, that nothing about it is stored, and that
nothing about it reaches the database.

**Architecture:** `PlacePicker size="compact"` mounts in a strip directly under the hero
banner: the banner names where you are, the strip changes it, and `SliceSelector` nests
below as *which shard of it*. Three state transitions get an owner — entering a place,
leaving it, and the two things that must clear it from elsewhere (a notification click and a
`/post/:postId` link). `scripts/check-place-entry.mjs` drives the whole walk in Chromium with
the 17-03 fixtures served by route interception, so it is deterministic and offline.

**Tech Stack:** React 19 · TypeScript 5.7 · Tailwind v4 · Playwright (**a global install —
not in `node_modules`**) · no test framework (see `17-SHARED.md`).

**Spec:** `17-CONTEXT.md` D-13, D-18, D-19; `17-RESEARCH.md` **Q3.5** (where place entry
lives, and why not `SliceSelector`), **Q3.4 item 3**, **Pitfalls 7 and 10**; `CLAUDE.md`
§ "Design rules" (the hit-test, the cookie, the global Playwright).

**Depends on:** 17-04. **Execute serially after it.**
🔴 **This plan and 17-06 both edit `AppShell.tsx`.** This one goes first.

**Carries:** D-13 (the enforcement half), D-18, D-19 (the second entry point); research
Q3.5, Q3.4 item 3, Pitfall 10.

### Task 1: `PlaceStrip` — under the banner, not inside it

**Files:**
- Create: `src/components/PlaceStrip.tsx`
- Modify: `src/components/AppShell.tsx` — `:1150-1165` (between the banner and the
  content-top marker)
- Reference (do not edit): `src/components/PlacePicker.tsx` (17-04),
  `src/components/HeroBanner.tsx` (**do not edit** — see below),
  `src/components/Sidebar.tsx`'s `LocationCard` (the vocabulary to echo)

- [ ] **Step 1: Where it goes, and the three places it does not**

The hero banner already names the place on screen. A control that changes that place belongs
immediately beneath it: *which place* → *which shard of it* → the feed. It is present at
every breakpoint (the banner renders for every `activeSlice`), on every tab, and it is
absent on Volunteer, which is correct — Volunteer is not a place.

Rejected, each for a recorded reason:

- 🔴 **Inside `HeroBanner`.** It is the component PR #92's bug lived in: a credit link under
  a padded content layer at `z-10`, correct while it was plain text, invisible to every
  screenshot and to `tsc -b`, broken only at `md` and up. It has its own layering and its own
  four-way checks. Put an interactive control into it and you inherit all of that. A sibling
  element in `AppShell` costs nothing and risks nothing.
- 🔴 **Inside `SliceSelector`.** Research Q3.5: two axes in one menu. It switches
  `sibling_index` within one `(slice_type, geoid)`; this switches `geoid` across every tab at
  once. Its copy is entirely about shards.
- **In the header.** Three grid tracks, and below 430px the wordmark is already `sr-only` to
  fit the existing controls. There is no room, and a control that collapses to an icon on
  phones is the wrong shape for something whose whole job is to say where you are.

- [ ] **Step 2: Two states, one component**

**Not visiting** (`viewedPlace === null`): a quiet, secondary affordance — *"Look at another
place"* — that opens `PlacePicker size="compact"`. 🔴 Secondary, not primary: for a signed-in
member on their own feed this is navigation they rarely want, and a prominent control here
would compete with the Post button two rows down.

**Visiting**: *"Looking at {place name}"* plus two controls — change the place (the same
picker) and **leave**. The leave control's label depends on the viewer:

- signed in → **Back to my spaces**
- signed out → **Back to the welcome screen**

🔴 **The name comes from the geoid, through `useJurisdictionName`** — the same hook and the
same cache the banner uses — never from the picker's input and never from an API label.
D-13, and 17-03 made it structural by giving `ResolvedPlace` no name field. While the name is
still resolving, show nothing rather than the tab label: `useJurisdictionName` answers
"City" until its offline shard lands, and *"Looking at City"* is worse than waiting a frame.
That is the same `name !== TAB_LABELS[tab]` idiom `ActiveExplore` already uses.

- [ ] **Step 3: The visiting state has to be unmistakable**

A member who forgets they are looking at Portland will read Portland's calendar as their own.
The feed is already gated and notices say why, but the strip is the thing on screen at all
times.

- Use the same amber vocabulary `ReadOnlyNotice` uses — the border/background pair written
  light **and** `dark:` together. Not a new colour, and not a new shape.
- Keep it one line on a phone at 390px; the place name truncates before the leave control
  does. 🔴 The control must never be the thing that falls off the row.
- ≥44px touch targets, `focus-visible` rings, `aria-live="polite"` on the place name so a
  screen reader is told the place changed.

- [ ] **Step 4: Build, look at it four ways, commit**

```bash
npm run build
npm run dev
git add src/components/PlaceStrip.tsx src/components/AppShell.tsx
git commit -m "feat(place): the shell's place control, under the banner

D-19's second entry point: the same PlacePicker, size=compact. Under the hero banner rather
than inside it — that component is where PR #92's unclickable credit link lived, and it has
its own layering and its own four-way checks; a sibling element in AppShell inherits none of
that. Not merged into SliceSelector either: two axes in one menu (research Q3.5). The place
name is resolved from the geoid through useJurisdictionName and is blank while that is
still answering, because 'Looking at City' is worse than waiting a frame."
```

### Task 2: The three transitions, and the two places that must clear a place

**Files:**
- Modify: `src/components/AppShell.tsx` — `:699-706` (`handleViewSlice`), `:726-747`
  (`openPost`), `:780-789` (the route effect), `:855-911` (`handleStartConversation`)

- [ ] **Step 1: `enterPlace`**

```ts
const enterPlace = useCallback((place: ResolvedPlace) => { … }, [])
```

It must do all four of these, and the last two are the ones that get forgotten:

1. `setViewedPlace(place)` and `writeViewedPlace(place)`.
2. 🔴 **Clear `viewingSlices` entirely.** It holds a shard index *within the member's own
   geoid*; while another place is on screen it means nothing, and leaving it set means
   leaving the place re-lands the member on a sibling shard they never chose.
3. 🔴 **Clear `activePostIds` entirely, and navigate to `/` if a thread is open.** The open
   thread belongs to the place being left. `handleStartConversation` already does exactly
   this when it re-targets a draft (`:891-895`) and says why: *"Leaving it open would render
   a sibling's post with `isViewOnly` cleared."* Same reasoning, wider case.
4. Reset the saved scroll offsets and call `scrollToContentTop()` — `handleViewSlice`
   (`:699-706`) is the model.

- [ ] **Step 2: `leavePlace`**

`setViewedPlace(null)`, `writeViewedPlace(null)`, and the same clears. For a signed-out
visitor this lands back on the welcome screen, because `showShell` goes false — no extra
branch needed.

Wire it to the strip's leave control **and** to `ReadOnlyNotice`'s `other-place` reason,
which 17-02 built with its control absent and 17-04 left that way. 🔴 That notice's control
was deliberately not wired until there was a handler; wiring it is this step and it is not
optional — a notice that explains a state and offers no way out is the stranding failure
research Pitfall 8 describes for the sibling case.

- [ ] **Step 3: 🔴 The two places that must clear a place from the outside**

Both are easy to miss, and both produce the same bug: a thread from the member's own slice
rendered inside a shell pointed at another city, with the gate computed against a slice that
is not on screen.

- **`openPost`** (`:726-747`), behind a notification click and every `/post/:postId` link.
  `locatePost` resolves against the member's **own** slices (`useNotificationRouting(slices)`
  — note it takes `slices`, not `onScreenSlices`, and **must keep taking `slices`**), then
  `handleTabChange(found.tab)` and `setViewingSlices(...)`. Add `setViewedPlace(null)` and
  the storage clear at the top, before `handleTabChange`.
- **The route effect** (`:780-789`) short-circuits on `!isAuthenticated`, so a signed-out
  visitor with a place on screen never reaches `openPost` — their link is stashed to
  `cs_pending_post` instead. 🔴 **Leave that behaviour exactly as it is.** The shared-link
  arrival is deferred and only Phase 18 changes the answer.

- [ ] **Step 4: `handleStartConversation`, while visiting**

It already refuses first (`:868`, now on `whyNoWrite`), and `canPostDraft(key, slices)`
already checks the **member's own** slices (17-04 Task 4). So a draft keyed to another place
is refused as `moved` and a draft keyed to the member's own place posts after
`leavePlace`-equivalent clearing.

🔴 **Verify the verdict path by hand rather than trusting it.** A draft started on the
member's own City, then a trip to another place, then back, then post — it must land in
their own City and the composer's context note must name their own place. If it names the
visited place, `destinationName` is being taken from `onScreenSlices` somewhere and that is
the wrong-jurisdiction anti-goal.

- [ ] **Step 5: Build, walk it, commit**

```bash
npm run build
npm run dev
```

The walk, signed in (`?dev=1`): own feed → strip → name another place → tabs, banner and
Explore follow → open a notification → **the place is gone and the thread is the member's
own** → the strip offers "Look at another place" again.

```bash
git add src/components/AppShell.tsx
git commit -m "fix(shell): entering and leaving a place clears everything that belonged to the other one

enterPlace and leavePlace each clear viewingSlices (a shard index within the member's own
geoid means nothing in another place) and activePostIds (the open thread belongs to the
place being left) — the same reasoning handleStartConversation already applies at :891.
openPost clears the place before it switches tabs: a notification click used to be able to
render the member's own thread inside a shell pointed at another city, with the gate
computed against a slice that was not on screen. The signed-out route effect is untouched:
the shared-link stash is deferred and only Phase 18 changes the answer."
```

### Task 3: `scripts/check-place-entry.mjs` — the committed browser check

**Files:**
- Create: `scripts/check-place-entry.mjs`
- Modify: `package.json` — `"check:place-entry": "node scripts/check-place-entry.mjs"`
- Reference (do not edit): `scripts/check-explore-gate.mjs` (the harness, `loadChromium`,
  `freshContext`, `bootedWithTheme`, `hitTest`, the `EXPECTED_NOISE` allowlist),
  `scripts/fixtures/place-search-*.json` (17-03)

🔴 **A separate script from `check:explore-gate`, and that is not a contradiction.**
`17-SHARED.md` says extend rather than fork — for the *same subject*. That script's subject
is "no write is offered"; this one's is "a place arrives, and nothing about it is kept or
sent". Different subjects, different failure messages, different things to read when one
goes red. 17-06 extends `check:explore-gate` for the write question.

- [ ] **Step 1: Deterministic, offline, by route interception**

Serve the 17-03 fixtures with Playwright's route interception:

- `**/api/essentials/location-search*` → `place-search-asheville.json`, and the empty
  fixture for a query that should miss.
- `**/api/essentials/coordinate-lookup` → the trimmed `coordinate-lookup-asheville.json`.

🔴 **Do not add a fixture path to the app to make this testable.** The app keeps one data
path; the check stubs the network. A `?placefixture=1` branch would be a fake-data route
shipped to production to serve a test, and `CLAUDE.md` is explicit that invented data does
not go in components.

🔴 **The fixtures are a contract snapshot and go stale silently.** 17-03's
`check-place-resolve.mjs --live` is what notices; say so in this script's header, with the
command, so someone debugging a green check against a changed API finds it.

- [ ] **Step 2: The control case, first, stated out loud**

Every assertion below is about an absence — nothing stored, nothing requested. All of them
are true of a page where the place never arrived.

So assert first, and stop if it fails:

1. The picker is on screen and reachable.
2. After choosing the Asheville row, the **hero banner names Asheville** and the Explore
   panel renders a non-empty `[data-explore-module]` list for a real geoid.
3. The tab list is the place's: City, County, State, Federal, Unified.

If this fails, say so and exit — the rest would be a true statement about nothing.

- [ ] **Step 3: 🔴 D-13, as two assertions a browser can actually make**

After a successful lookup, with a query string the check chose so it cannot collide with
anything else on the page (a nonsense token, not "asheville"):

1. **Nothing stored.** Dump **every** key and value of `localStorage` **and**
   `sessionStorage`, concatenate, and assert the token appears nowhere — case-insensitively,
   and also with the URL-encoded and whitespace-stripped forms, because a stored value may
   have been normalised on the way in. Then assert `cs_viewed_place` parses and its keys are
   exactly the five of `ResolvedPlace`.
2. **Nothing echoed.** Assert the token appears nowhere in `document.body.innerText` once
   the place has loaded. 🔴 Clear the picker's own input first, or the check reads the
   visitor's own typing back and fails for the wrong reason — which is worse than failing,
   because it looks like a finding.

- [ ] **Step 4: 🔴 Nothing about the place reaches the database**

Record every request the page makes (`page.on('request')`) from the moment the place is
chosen, and assert that **no URL containing `/rest/v1/`** carries the visited geoid, the
`place:` sentinel, or `slice_id=eq.place`.

This is the assertion that catches the one mistake with a silent failure mode: wiring the
conversations feed, the member directory, or `useSiblingSlices` to a visited place. In Phase
17 every one of those returns zero rows or an error rather than failing loudly, and zero rows
reads as *"nobody has said anything here"*.

Also assert the **positive** half, so the check is not vacuous: at least one request **was**
recorded (the page is doing something) and the two stubbed `/api/essentials/` routes were
hit the expected number of times — `location-search` more than once if the check typed more
than one query, `coordinate-lookup` **exactly once**, because it is 100 KB and ~1.2 s and
must never be in the typeahead.

- [ ] **Step 5: The place states a place can be in**

| # | Assertion |
|---|---|
| 1 | Control case (Step 2) |
| 2 | Signed out: the welcome screen renders; after choosing a place, the shell does |
| 3 | 🔴 The conversations view for a visited place shows the honest state and renders **zero** post cards and **zero** composer affordances |
| 4 | The place survives a reload (`sessionStorage`), and the welcome screen does **not** come back |
| 5 | A fresh context with no stored place lands on the welcome screen |
| 6 | 🔴 An **unincorporated** place — the `arden` county row, resolved through the county branch — yields **four** tabs and no City, and nothing on screen reads as an error |
| 7 | The no-results fixture produces the honest line, not a blank list and not a nearest match |
| 8 | Signed in (`?dev=1`): the strip enters a place, and **leave** returns to the member's own tabs and own banner |
| 9 | Signed in, visiting: a `/post/<own post id>` deep link clears the place, opens the member's own thread, and the strip is back to "Look at another place" |
| 10 | Hit-test: the picker input, the first option row, and the strip's leave control resolve to themselves at **1440 and 390**, in **both themes**, with `documentElement.classList` asserted each time |
| 11 | Keyboard only: tab, type, ↓, Enter loads the place; Escape closes the list and keeps the text |
| 12 | `localStorage` and `sessionStorage` blocked: the welcome screen still renders, a place still loads for the session, and **nothing throws** (Pitfall 10) |
| 13 | Zero uncaught page errors and zero unexpected console errors throughout |

🔴 **Assertion 12 needs a real block, not a mocked one.** Override `Storage.prototype.setItem`
and `getItem` to throw via `page.addInitScript`, before the app boots. A `try`/`catch` that
was never exercised is the same as one that is not there.

- [ ] **Step 6: Theme, viewport and Playwright, done the repo's way**

- `ev_color_scheme` set on the **context**, and `documentElement.classList.contains('dark')`
  asserted against what was asked for. 🔴 Playwright's `colorScheme` option does nothing in
  this app.
- Playwright resolved via `npm root -g`, imported as `mod.chromium ?? mod.default?.chromium`.
  Copy `loadChromium` from `check-explore-gate.mjs` rather than writing a third version.
- `EXPECTED_NOISE` reused, and the suppressed lines printed, so the allowlist cannot become
  a place a real error hides.

### Task 4: 🔴 Prove each gate separately

One at a time, restoring between, with the matrix in the commit body.

| Revert | Expected red |
|---|---|
| `writeViewedPlace` storing the picker's raw query alongside the geoids | **D-13 assertion 1 only** — the thing the whole clause exists to prevent |
| the place name rendered from the picker's input rather than from the geoid | D-13 assertion 2 |
| the conversations panel's `!isVisitingPlace` guard removed | the network assertion **and** assertion 3 — a PostgREST request carrying the `place:` sentinel, and post cards on screen |
| `coordinate-lookup` called from inside the typeahead | the exactly-once assertion |
| `enterPlace` not clearing `activePostIds` | assertion 9 |
| the strip's leave control removed | assertions 8 and 10 |
| the `try`/`catch` removed from `viewedPlace.ts` | assertion 12 — and the page will go blank, which is the point |
| the `arden` county row resolved through the place branch | assertion 6 |

🔴 The first row is the one to run slowly. It is the only mechanical demonstration in the
phase that D-13 is enforced rather than intended, and it is also the exact shape a
well-meaning future change takes — *"let's remember what they typed so the box is not empty
when they come back"*.
