# Phase 17-01 — Reaching the signed-out app, and the one predicate the gate will hang on

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development

> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the two things every later plan is unverifiable without: a way to actually
*be* signed out on localhost, and a pure, import-free module that answers "may this viewer
write here?" — failing closed, with no React, no network, and no copy of itself anywhere.

**Architecture:** Two small additions and no behaviour change on screen. `useAuth.ts` gains
a dev-only `?signedout=1` that clears the session and *stays* cleared across a wouter
navigation. `src/lib/writeAccess.ts` is new, has no runtime imports, and holds one primitive
— `whyNoWrite()` — that `canWriteIn()` and the UI's notice copy both derive from.
`scripts/check-write-access.mjs` loads the **shipped** module with
`node --experimental-strip-types` and tables every input against its expected answer. No
component consumes any of it yet; 17-02 does that.

**Tech Stack:** TypeScript 5.7 (`strict`, `noUncheckedIndexedAccess`) · React 19 · Vite 6 ·
Node 24 `--experimental-strip-types` · no test framework (see `17-SHARED.md`).

**Spec:** `17-CONTEXT.md` (D-01, D-04, D-20, D-21), `17-RESEARCH.md` **Q3.4** and
**Q3.6** and **Pattern 1** — read Q3.4's four-row table before Task 2, it is this module's
specification — plus Pitfalls 1 and 10, and `ROADMAP.md` § Phase 17's third scope bullet.

**Depends on:** nothing. First plan in the phase.

## Why this is Wave 0 and not an afterthought

Two independent blockers, both discovered by reading rather than by running:

1. 🔴 **On a fresh clone you cannot be signed out, and no committed check can be.**
   `useAuth.ts:219-225`:

   ```ts
   if (import.meta.env.DEV && (… .get('dev') === '1' || !import.meta.env.VITE_SUPABASE_URL)) {
     localStorage.setItem('cs_token', createDevFallbackToken())
     setAuthState({ userId: DEV_GUEST_ID, isAuthenticated: true, isLoading: false })
   ```

   With no `VITE_SUPABASE_URL` — the fresh-clone state `CLAUDE.md` documents — the app signs
   **itself** in, and dropping `?dev=1` changes nothing.

   ⚠️ **On a machine that already has a `.env.local`, the signed-out branch is reachable
   today**: `VITE_SUPABASE_URL` is set, so the dev-guest branch needs `?dev=1`, and without
   it the silent-SSO check fails from localhost and the guest UI renders. That does not make
   this task optional — it makes it *necessary*. 17-02 and 17-06 both boot a **committed**
   check at `?signedout=1`, and a check that passes only on machines carrying somebody's
   `.env.local` is not a check; it is a memory, which is the thing `16-VALIDATION.md` says
   a committed script exists to stop being. Every browser check and every screenshot in
   plans 02 and 04 through 07 needs this task.

2. 🔴 **The gate must be a function, not an expression at a call site.** Research Q3.6
   item 3: if the rule is written inline wherever it is needed, then D-21's cross-slice
   Empowered authorship later means finding every call site again — and, more immediately,
   a check can only test a transcription of the rule rather than the rule. The project
   already has the answer: `src/lib/exploreComposition.ts` is pure and import-free precisely
   so `scripts/check-composition.mjs` can run the shipped functions, and its header says
   why: *"A copy-test passes while the shipped code is wrong."*

### Task 1: `?signedout=1` — a dev-only way to be a visitor

**Files:**
- Modify: `src/hooks/useAuth.ts` — the `resolveAuth` body (`:176-231`)
- Reference (do not edit): `src/lib/devMockData.ts:89-115` (`resolveDevPlace`, the

- [ ] **Step 1: Resolve the flag once, guarded, before anything else**

Add a module-level resolver modelled line-for-line on `resolveDevPlace()`:

- Only under `import.meta.env.DEV`, read with the same `try`/`catch`-wrapped
  `import.meta.env` access `devBuild()` uses — this module is not loaded by
  `--experimental-strip-types` today, but the guard costs nothing and the next check script
  that reaches for it will not have to add one.
- `?signedout=1` in the query string sets a `sessionStorage` key (suggested
  `cs_signed_out`), wrapped in `try`/`catch`.
- With no query parameter, a previously stored key still counts.

🔴 **Session scope, and a stored key, are both load-bearing.** wouter drops the query string
the moment it navigates to `/post/:postId` or `/profile/:userId`, so a flag read only from
`location.search` silently signs the visitor back in mid-walk — and plan 17-05's checks walk
exactly that path. Session rather than local, for the same reason `cs_dev_place` is: the
choice should not outlive the window.

🔴 **Guard every access.** `resolveDevPlace()` is the template; do not add a second instance
of the unguarded write at `useAuth.ts:100` (deferred item 9, still open — see
`17-SHARED.md`).

- [ ] **Step 2: Act on it FIRST in `resolveAuth`, and say why that is safe**

Insert before the hash check at `:178`:

```ts
// Dev-only, and checked FIRST — the one place that reverses the ?dev=1 ordering rule.
if (isDevSignedOut()) {
  try { localStorage.removeItem('cs_token') } catch { /* storage blocked — nothing to clear */ }
  setAuthState({ userId: null, isAuthenticated: false, isLoading: false })
  return
}
```

🔴 **`CLAUDE.md` says the `?dev=1` token is "checked last … so a real session always wins",
and this deliberately goes first. Write the reason in the code, not only here.** The
asymmetry is the whole justification: `?dev=1` **grants** a session, so it must never
outrank a real one; this flag only ever **removes** one, so there is no privilege it can
confer and nothing it can mask. It is also behind `import.meta.env.DEV`, so Vite drops the
branch from a production build entirely.

The `removeItem` matters as much as the state: `?dev=1` persists its fallback token to
`localStorage`, so without the clear, step 2 of the existing flow (`:191`) would read that
token back on the very next reload and sign the visitor in again.

- [ ] **Step 1: The header, which is a constraint and not a comment**

Open the file with the same 🔴 note `exploreComposition.ts` carries: **no runtime imports,

- [ ] **Step 2: The types**

```ts
/** A slice as it appears ON SCREEN. `id` is null for a place with no slice row. */
export interface ViewedSlice {
  /** The `slices.id` when a row exists for this place and level, else null. */
  id: string | null
  sliceType: string
  /** null only for a placeless type whose geoid the shell does not carry. */
  geoid: string | null
}

export type NoWriteReason = 'signed-out' | 'no-slice' | 'other-place' | 'sibling-shard'
```

🔴 **`id: string | null`, and that is the point.** Research Q3.3: slice rows are created on
demand by `/assign`, which only runs for a signed-in Connected member — so a
`(city, <geoid>)` row exists **only where a member already lives**, and 15 rows exist in the
entire product. Most places a visitor names have no row at all. A type that insists on a
string would force a synthetic id somewhere, and a synthetic id in an `ownedSliceIds` lookup
is a coin toss. Null is the honest value and it fails closed for free.

- [ ] **Step 3: `placeKey` — the read key, which is not the write key**

```ts
/** `(slice_type, geoid)` — the key a jurisdiction's shards all share. */
export function placeKey(sliceType: string, geoid: string | null): string {
  return `${sliceType}|${geoid ?? ''}`
}
```

🔴 **Do not reuse `compositionKey()` from `exploreComposition.ts`.** It collapses
`federal` / `unified` / `volunteer` to the slice type alone, which is correct for choosing
Explore content and wrong here: this key has to distinguish *places*, and a deliberate
normalisation that erases geoids is the last thing a place comparison should inherit. Two
keys, two jobs, no shared function. Say so in a comment, because they look alike.

- [ ] **Step 4: `whyNoWrite` — the primitive**

One function, one body, four cases:

```ts
export interface WriteContext {
  /** The slice on screen, or null when nothing is. */
  viewed: ViewedSlice | null
  /** Every slices.id the viewer is a member of. Empty for a guest AND for an Inform account. */
  ownedSliceIds: ReadonlySet<string>
  /** placeKey() for every slice the viewer holds. Lets a sibling shard be told from another place. */
  ownedPlaceKeys: ReadonlySet<string>
  /** False for a visitor with no session at all. */
  isAuthenticated: boolean
}

export function whyNoWrite(ctx: WriteContext): NoWriteReason | null
```

The rules, in this order — and the ordering is what makes the reasons useful rather than
merely correct:

1. `!ctx.isAuthenticated` → `'signed-out'`. First, because it is the only reason whose
   remedy is "sign in".
2. `!ctx.viewed || !ctx.viewed.id` → `'other-place'` **when the viewed slice has a geoid the
   viewer holds no slice for**, else `'no-slice'`. A null id means there is no row to be a
   member of; which of the two reasons it is depends on whether the viewer holds *this
   level* elsewhere.
3. `ctx.ownedSliceIds.has(ctx.viewed.id)` → `null`. They may write.
4. `ctx.ownedPlaceKeys.has(placeKey(viewed.sliceType, viewed.geoid))` → `'sibling-shard'`.
   Same jurisdiction, different shard — the Phase 16 state, unchanged.
5. Otherwise → `'other-place'`.

🔴 **There is no `tier` term and there must never be one.** D-04 says an Inform account
receives exactly what an anonymous visitor receives. An Inform account holds no
`slice_members` rows, so its `ownedSliceIds` is empty and it lands in branch 2 or 5 by
construction — D-04 is satisfied by the data rather than by a rule someone has to remember
to write. Adding `if (tier === 'inform')` here would make it a rule someone can later
delete. Put that in the doc comment.

🔴 **Fails closed, and the ordering of 2 before 3 is why.** The expression this replaces,
`!!activeSlice && !!activeViewing && …`, answers `false` — "not gated" — when there is no
slice at all. Here, absence of a slice reaches a `return` with a reason in it before any
membership test runs.

🔴 **This function body is D-21's seam.** Empowered cross-slice reach belongs **here** and
nowhere else: one body changes and every consumer inherits it. Write that in the doc
comment, with D-21 named, or the next person adds `|| isEmpowered` at a call site.

- [ ] **Step 5: `canWriteIn` and `canReadConversationsIn`**

```ts
export function canWriteIn(ctx: WriteContext): boolean {
  return whyNoWrite(ctx) === null
}
```

Derived, never parallel. Two functions that each decide the same thing is the shape the
`current_user_id()` incident already punished this codebase for.

```ts
/**
 * May this viewer READ the conversations in the slice on screen?
 *
 * 🔴 NOT the same question as canWriteIn. A sibling shard is readable and not
 * writable — posts_select_sibling_slice joins on (slice_type, geoid), so every
 * shard of a jurisdiction the viewer belongs to is readable today.
 *
 * 🔴 PHASE 18 CHANGES THIS FUNCTION'S BODY AND NOTHING ELSE. Once civic_spaces
 * grants anon schema USAGE and posts_select_public lands, every caller may read
 * every slice and this returns true unconditionally (minus whatever that phase
 * decides about deleted posts and suspended authors). Until then it is false for
 * another place and for a visitor, and the UI must say so rather than render an
 * empty feed — an empty feed returned by RLS reads as "nobody said anything here".
 */
export function canReadConversationsIn(ctx: WriteContext): boolean
```

Body: `false` when `!ctx.isAuthenticated` or `!ctx.viewed`; otherwise
`ctx.ownedPlaceKeys.has(placeKey(ctx.viewed.sliceType, ctx.viewed.geoid))`.
