# Phase 17-04 — The welcome screen, and a named place on screen

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A visitor who is not signed in lands on an explainer that says what Civic Spaces
is, what an account is for, what they cannot do *yet*, and why an address is safe to type —
then names a place and sees that place's real City, County, State, Federal and Unified
Explore. Never a placeless shell again.

**Architecture:** One screen, one picker, one state. `WelcomeScreen` replaces the signed-out
branch at `AppShell.tsx:1063` — the grey sentence, the button, and the 580 words of
`geoid: null` Explore all go (D-09). `PlacePicker` is the mechanism, built once here and
mounted a second time in the shell by 17-05 (D-19: one mechanism, two entry points).
`viewedPlace` is new `AppShell` state, hydrated from `sessionStorage`, and
`onScreenSlices = viewedPlace ? placeSlices(viewedPlace) : slices` is the one substitution
that makes the existing shell — tabs, nav rail, hero banner, Explore — follow a visited
place without those components learning anything new.

**Tech Stack:** React 19 · TypeScript 5.7 · Tailwind v4 (class-based dark, **dark is the
default**) · `motion/react` · TanStack Query · no new packages (see `17-SHARED.md`).

**Spec:** `17-CONTEXT.md` D-05, D-06, D-09, D-10, D-11, D-12, D-15, D-16, D-17, D-18, D-19,
D-25 and § "Specific Ideas"; `empowered-vote-primer.md` § **The Three Pillars** (the

quotes), **Q3.2**, **Q3.3**, **Pitfalls 8 and 11**; `ROADMAP.md` § Phase 17's measured

## 🔴 The copy must be true in Phase 17, not in Phase 18

This is the single easiest thing to get wrong in this plan, because `17-CONTEXT.md` is full
of the *destination* and this phase is the halfway house.

**In Phase 17, conversations are still members-only.** Every `civic_spaces` grant is
`TO authenticated`; `posts_select_sibling_slice` requires `geoid` equality. An observer
reads zero forum rows, and so does a signed-in member looking at another city. D-07's
"observation covers Explore *and* conversations" and D-08's "fully public, and scrapable"
are **Phase 18**.

So, forbidden on this screen until Phase 18 ships:

- anything that says conversations are public, open, readable by anyone, or scrapable
- anything implying a post will be findable — 🔴 D-25 and Pitfall 11: this is a
  client-rendered Vite SPA with no SSR, no prerender, no `robots.txt` and one static set of
  `og:` tags. Crawlable is not indexed even after Phase 18, and the exposure that phase
  creates is the **PostgREST endpoint**, not the pages. Never write "search", "searchable",
  "on Google" or "shareable link that shows the post"
- 🔴 D-17: never *anonymous*, never *untraceable*. D-02 is explicit that Connect privacy is
  not protection from consequence — there is a paper trail, and that is how mis- and
  disinformation sources are identified. The honest word is **private from other members**

What **is** true today and is the pitch: anyone can look at any place's Explore — what its
government is working on, who represents it, when it votes next — and conversations are the
part an account opens.

🔴 **One paragraph of this screen is Phase 18's to revise.** Mark it in the source with a
comment naming Phase 18, and record it in `17-VALIDATION.md` § Known gaps, so that phase can
find it with a grep instead of a re-read.

### Task 1: `PlacePicker` — one mechanism, two sizes

**Files:**
- Create: `src/components/PlacePicker.tsx`
- Reference (do not edit): `src/hooks/usePlaceSearch.ts`, `src/hooks/usePlaceResolve.ts`,
  `src/lib/placeResolve.ts` (17-03), `src/components/SliceSelector.tsx` (the repo's existing
  listbox: `aria-haspopup="listbox"`, `role="option"`, outside-click close),
  `src/components/explore/exploreUi.tsx` (`PrimaryButton`, `CARD`)

- [ ] **Step 1: One component, two sizes — not two components**

D-19 is explicit: *"the place-entry mechanism cannot be built only into the signed-out
welcome screen — it is shell-level navigation available to a signed-in member too. Plan it
as one mechanism with two entry points, not two features."*

`PlacePicker({ size: 'hero' | 'compact', onResolved, onCancel? })`. `size` changes padding,
type scale and whether the label renders visibly — nothing else. 17-05 mounts `compact`
and must not need a prop that changes behaviour.

🔴 **Not inside `SliceSelector`, and not beside it in the toolbar.** Research Q3.5: that
control switches `sibling_index` **within** one `(slice_type, geoid)`; this one switches
`geoid` across every tab at once. Its copy ("Your Community · Slice 3", "This is the only
slice in Asheville so far") is entirely about shards. Merging them produces a menu where two
adjacent items mean different kinds of thing. They nest — *which place*, then *which shard
of it* — and they stay separate controls.

- [ ] **Step 2: The combobox, done properly**

A `<label>` with `htmlFor` — 🔴 **never a placeholder as the label**; a placeholder vanishes
on focus and is not an accessible name. Then:

- `role="combobox"`, `aria-expanded`, `aria-controls` pointing at the listbox,
  `aria-autocomplete="list"`, and `aria-activedescendant` naming the highlighted option.
- The listbox is `role="listbox"` with `role="option"` children and `aria-selected`.
- Keyboard: ↓/↑ move the active option, Enter chooses it, Escape closes the list and keeps
  the text, Tab leaves. 🔴 Mouse-only selection is the failure the repo's own guidance names
  — a click handler without a key handler.
- `aria-live="polite"` on a visually-hidden status line that announces the result count and
  the no-results state. An async list that updates silently is invisible to a screen reader.
- `autocomplete="off"` on the input, with a one-line reason in the source: the browser's own
  autofill dropdown renders **over** the listbox. That is the documented exception to "never
  block autofill"; there is no autofill token for a place search.
- `type="search"`, so phones offer a sensible keyboard and a clear affordance.

- [ ] **Step 3: The four states, each with something on screen**

| State | What it shows |
|---|---|
| idle | the label, the input, and one line of help naming **both** accepted inputs (see Step 4) |
| searching | a skeleton matching `FeedSkeleton`'s vocabulary, in the listbox. 🔴 Not a third loading style, and not a frozen input |
| results | up to 8 rows, each showing the label and the area type the API already returns, so "Portland, OR · City" and "Portland, ME · City" are told apart |
| **no results** | 🔴 the honest answer and a way forward — *"Nothing matched. Try the place's name, or its county."* **Never a blank list, never a guess, and never a nearest match.** CLAUDE.md's rule for volunteers is the rule here: if a request fails, say so and stop |

🔴 **The resolve step can fail after a row is chosen** — the centroid leg (17-03) can come
back with no county. That is a *different* failure from "no results" and needs its own line,
because retyping the same name will not fix it. Say what happened and leave the chosen row
visible so the visitor can pick a different one.

- [ ] **Step 4: The address input, present only when it can work**

`PLACE_RESOLVE_ENABLED` (17-03) is `false` until ev-accounts ships
`POST /api/civic-spaces/resolve`.

- **False:** the picker takes a **place name only**. The help line says so plainly — *"a
  city, town or county"* — and **no address field renders at all**. No disabled control, no
  "coming soon", no copy promising a path that cannot run. A dead control is the specific
  failure `check:explore-rooms` exists to catch.
- **True:** a second input, or a toggle, accepts a street address and posts it to the
  resolver. Same four states; the resolver's `ADDRESS_NOT_FOUND` / `PO_BOX_REJECTED` /
  `GEOCODER_UNAVAILABLE` each get an honest line, and every one of them offers the
  place-name path as the escape hatch — which is right, because a PO box, a rural route and
  an unmapped new build all have a place name and no usable street address.

🔴 **The typed string is never rendered back, in either path.** Not in a confirmation, not
in a heading, not in a toast. D-13. After resolution the screen names the place from its
**geoid**, through `geoNames.ts` — and 17-03 made that structural by giving `ResolvedPlace`
no name field at all.

- [ ] **Step 5: Mobile-first details that are easy to lose**

- 🔴 **The input's font-size must be at least 16px on mobile.** Below that, iOS Safari zooms
  the page on focus and does not zoom back — the first interaction on the screen, broken.
- Every option row is a ≥44px touch target.
- `focus-visible:ring-2` on the input and on every option. Never `outline-none` alone.
- `motion/react` for the list, and respect `prefers-reduced-motion`. 🔴 `motion` at this
  version does not **declare** `useReducedMotion` in its types — `SeedInvitationModule`
  records exactly this and chose no animation rather than an unguarded one. Do the same, or
  use a CSS `@media (prefers-reduced-motion: reduce)` rule, which typechecks fine.
- Every colour written light **and** `dark:` together. `gray-400` is decoration only in
  light; `gray-500` fails AA on dark.

- [ ] **Step 6: Build and commit**

```bash
npm run build
git add src/components/PlacePicker.tsx
git commit -m "feat(place): one place-entry mechanism, two sizes

D-19: place entry is shell navigation, not a guest feature, so this is one component the
welcome screen and the shell both mount. Deliberately NOT merged into SliceSelector, which
switches sibling_index within one (slice_type, geoid) while this switches geoid across
every tab — two axes in one menu is a control where adjacent items mean different kinds of
thing. The address input does not render at all until VITE_PLACE_RESOLVE_URL is set: a
disabled control promising a path that cannot run is the dead-control failure 16-08's check
exists to catch. No results is an answer with a way forward, never a nearest match."
```

- [ ] **Step 3: The three blocks**

**1 — Look anywhere.** True today, and the thing that makes the screen generous rather than
a wall. Name what is actually there: what a place's government is working on, who represents
it, what is on its calendar, when it votes next. D-18.

**2 — Speak where you live.** Posting, replying and voting belong to the people who live
under that government. 🔴 **Name both walls** — the ROADMAP measured that "Make an account"
is not the whole instruction and will strand anyone who stops there: Civic Spaces needs the
**Connected** tier, and Connected means **an address has been set**, because slice
assignment runs off encrypted coordinates. Then D-11's word: *not yet* — the visitor should
know the ceiling before they press something, not by pressing it.

**3 — What happens to an address.** D-15 and D-16, and this is the block most likely to
drift into overclaiming. The honest version, and all of it is true:

- It is geocoded **once**, to work out which boundaries it falls inside, and then it is
  gone: not stored, not shown back, not in any profile Civic Spaces holds.
- Civic Spaces only ever learns the **geoids** — the platform's own governing principle is
  *"A boundary geoid is a category, an address is not."*
- Posting under a handle keeps your name **private from other members**.

🔴 And the three things this block must not say, each for a reason already decided:

- not *"your address never leaves your browser"* — research Q1.8: the geocoder's host sees
  it on every path, GET or POST, and the member path has the same property. D-16's claim as
  written — *geocoded once and never kept* — is true and must not be allowed to grow.
- not *anonymous*, not *untraceable*, not *nobody can ever know* — D-17, D-02.
- nothing about conversations being public or findable — see the boxed note above.

- [ ] **Step 4: Four-way, from the first line of markup**

- Dark is the **default**. Write every colour light **and** `dark:` together, in the same
  class string. A `dark:`-only colour is a bug here more than anywhere, because this is the
  first screen a stranger sees.
- Light body text `gray-600`/`gray-900`; dark body text `gray-300`/`gray-400`. 🔴 Never
  `gray-500` on dark (3.67:1 on `gray-900`) and never `gray-400` on light (2.54:1 on white
  — under the 3:1 even a meaningful icon needs).
- Headline sizes that work at 390px without a horizontal scrollbar, and line length capped
  around 65–75 characters at desktop width — a `max-w-prose`-ish container, not the full
  grid.
- Brand tokens only: `brand`, `brand-btn`, `brand-hover`, `brand-muted`, `brand-light`,
  `brand-coral`, `brand-coral-text`. No new colours.
- Any decorative SVG is `aria-hidden`. 🔴 **No emoji as an icon** — the repo has an `Emoji`
  component for content and SVG for UI marks; keep that line.

Do not skip the looking. A clean build proves nothing about a screen whose entire job is to
read well.

🔴 **A separate state, never `viewingSlices`.** Research Q3.4 item 3: `viewingSlices` holds a

- [ ] **Step 2: `placeSlices` — a place as the shell already understands one**

```ts
/**
 * A visited place, shaped as the Partial<Record<SliceType, SliceInfo>> the whole
 * shell already consumes — so tabs, the nav rail, the hero banner, population,
 * weather, elections, meetings and Explore all follow it with NO change to any
 * of them.
 *
 * 🔴 `id` is a `place:<type>:<geoid>` sentinel and is NEVER a slices.id.
 *   - Phase 17 makes no Supabase request for a visited place. Every grant is

 *     joins on geoid, so a signed-in member reads nothing in another city either.
 *     Both are Phase 18's to open.
 *   - The sentinel is deliberately shaped so a leak is loud: it is not a UUID and
 *     not a `mock-` id, so a query built from it fails visibly rather than
 *     returning zero rows that read as "nobody has said anything here".
 *   - canWriteIn() never matches it, because ownedSliceIds holds real ids only.
 */
function placeSlices(place: ResolvedPlace): Partial<Record<SliceType, SliceInfo>>
```

Entries: `city` (only when `place.city` is non-null — 🔴 an unincorporated place gets four
tabs, and that is an answer), `county`, `state`, `federal` with geoid `'US'`, `unified` with
geoid `'UNIFIED'`. Never `volunteer` — role-gated, never a visitor's.

`memberCount: 0` and `siblingIndex: 1` are placeholders; `photoUrl: null` so `useHeroBanner`
resolves the shared-library banner for the geoid, exactly as it does for a member.

- [ ] **Step 5a: Two defences, and both are needed**

**At the hook**, so no future caller can reintroduce it. `useSiblingSlices` already bails on
a fixture id via `isMockSliceId`; add a second bail for the place sentinel:

```ts
if (isPlaceSentinelId(ownSliceId)) return { siblings: [], isLoading: false, isError: false }
```

🔴 **Empty, NOT `getMockSiblings`.** The mock branch returns fixture siblings, and routing a
real place into it would show a stranger **invented shards of their own city**. That is
worse than showing none — it is the "a real answer for the wrong place" failure with the
fixture switch flipped to produce it. The two bails look alike and must not be merged.

🔴 **Put both the sentinel's constructor and `isPlaceSentinelId` in `src/lib/viewedPlace.ts`,
not in `AppShell.tsx`.** `AppShell` imports `useSiblingSlices`; if the hook had to import
the predicate back out of `AppShell` that is a cycle, and the executor will discover it as
a confusing runtime `undefined` rather than as a build error. `viewedPlace.ts` already owns
the place concept, has no React imports and is imported by both. One file defines the

**At the render**, because not querying is a different requirement from not offering. Guard
