# Slice Taxonomy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a slice a government a member lives under — Unified, Federal, State, County, City — instead of a constituency they vote in, so the product stops contradicting its own UI copy and a member in any US community gets spaces created on demand.

**Architecture:** Three parts, in order. First make the member counter trustworthy, because the slice capacity check reads it and is currently sharding on fiction. Then extend the accounts jurisdiction RPC to return the city, state and nation geoids the new mapping needs — additive, so it ships alone with no consumer. Then cut the taxonomy over in one coordinated deploy: rename the slice types, repoint the assigner, and migrate the 16 existing slices and 12 posts.

**Tech Stack:** TypeScript/Node 20, Express, Supabase (Postgres 17 + PostGIS), React 19 + Vite 6, vitest (EV-Accounts; added to the assignment service by this plan).

**Spec:** `.planning/research/SLICE-TAXONOMY.md`

**Repos:** This plan spans two. Tasks 2–3 are in `C:\EV-Accounts`. All others are in `C:\Civic Spaces`.

## Global Constraints

- **Slice capacity is 6,000 members**, enforced in two places that must agree: the
  `civic_spaces.enforce_slice_cap()` trigger (`IF v_count >= 6000`) and the service's
  `findActiveSliceForGeoid` query. A member's five spaces sum to ~30,000; that is the
  ~30,000 principle, not the size of one room.
- **Levels are optional.** A jurisdiction can lack a city (unincorporated) or a school
  district. Missing levels are skipped, never fatal. Arden, NC has no `G4110` place.
- **Never pair a `geo_id` with the wrong `mtfcc`.** `essentials.districts` reuses geo_ids
  across layers — `48008` is both `STATE_UPPER` and `STATE_LOWER`, and `48085` is both a
  county and `TX House District 85`. Every boundary lookup filters on `mtfcc`.
- **EV-Accounts migrations use the `CC_` namespace** (Chris Cantrell). Take the number
  LAST: write as `CC_wip_*.sql`, then `git fetch origin && npm run check:migrations
  --prefix backend`, then rename, apply and commit in one go. Highest seen 2026-09-01 is
  `CC_0030`.
- **Civic Spaces migrations** are `supabase/migrations/YYYYMMDDHHMMSS_name.sql`.
- **Tasks 5, 6 and 7 deploy together.** They are a coordinated cut. With 7 members and 12
  posts, a short window beats dual-support complexity.
- 🔴 **HARD GATE: Task 3 must be live in production before Task 6 deploys.** Task 6 makes the
  assigner read `j.nation / j.state / j.city`. If the accounts API is not yet returning those
  keys, every geoid is `undefined`, the null guard skips all four levels, and new members are
  assigned **only Unified** — worse than today's failure. Verify with a live call, not with a
  merged PR:
  `curl -s -H "Authorization: Bearer $TOKEN" https://accounts-api.empowered.vote/api/account/me | jq .jurisdiction`
  and confirm `city`, `state` and `nation` are present.
- 🔴 **Task 7 snapshots before it deletes.** It is the only destructive step and it runs on
  production. The `BEGIN/ROLLBACK` dry-run protects the rehearsal, not the real run.

## Task 1: Make the member counter trustworthy

`slices.current_member_count` does not match reality — `federal/0636` claims 42 against 1
real member, `local/06037` claims 36 against 1, `neighborhood/0622710` claims 23 against 0.
Both the capacity check and the hero banner read it, so a slice holding three people can be
declared full and split a community that never needed splitting.

The triggers themselves are correct (`enforce_slice_cap` increments on insert,
`decrement_slice_count` decrements on delete), so this is a one-time repair plus a guard.

**Files:**
- Create: `supabase/migrations/20260902000000_reconcile_slice_counts.sql`

**Interfaces:**
- Consumes: nothing
- Produces: `civic_spaces.current_member_count` equals `count(slice_members)` for every slice

- [ ] **Step 1: Write the migration with a post-verify gate that fails if it did not work**

```sql
-- Reconcile slices.current_member_count against actual membership.
--
-- The counter is maintained by triggers (enforce_slice_cap on INSERT,
-- decrement_slice_count on DELETE) and those are correct. The drift predates them:
-- measured 2026-09-01, federal/0636 claimed 42 members against 1 real,
-- local/06037 claimed 36 against 1, neighborhood/0622710 claimed 23 against 0.
--
-- This matters beyond display. enforce_slice_cap reads this column, so sharding
-- decisions were being made on fiction: a slice holding three people could be
-- declared full and spawn a sibling, splitting a community that never needed it.

UPDATE civic_spaces.slices s
SET current_member_count = COALESCE(m.n, 0)
FROM (
  SELECT sl.id, COUNT(sm.user_id) AS n
  FROM civic_spaces.slices sl
  LEFT JOIN civic_spaces.slice_members sm ON sm.slice_id = sl.id
  GROUP BY sl.id
) m
WHERE m.id = s.id
  AND s.current_member_count IS DISTINCT FROM COALESCE(m.n, 0);

DO $$
DECLARE v_wrong integer;
BEGIN
  -- Count the disagreeing slices, not the rows within one group. A GROUP BY/HAVING
  -- with SELECT INTO assigns only the first group's count and leaves v_wrong NULL
  -- when every slice is correct, which reads as a pass for the wrong reason.
  SELECT COUNT(*) INTO v_wrong FROM (
    SELECT sl.id
    FROM civic_spaces.slices sl
    LEFT JOIN civic_spaces.slice_members sm ON sm.slice_id = sl.id
    GROUP BY sl.id, sl.current_member_count
    HAVING sl.current_member_count <> COUNT(sm.user_id)
  ) bad;

  IF v_wrong > 0 THEN
    RAISE EXCEPTION 'reconcile failed: % slices still disagree with their membership', v_wrong;
  END IF;
END $$;
```

## Task 2: Return city, state and nation from the jurisdiction RPC

`connect.resolve_user_jurisdiction` returns congressional, state_senate, state_house,
county, school_district, city_council and municipality. The new mapping needs a **city**, a
**state** and a **nation** geoid, and neither existing key supplies a usable city:
`municipality` looks for `district_type = 'LOCAL_EXEC'`, which Plano has none of, and
`city_council` orders `X%` rows first so in Austin it returns a council district rather than
the city.

Resolve all three straight from `geofence_boundaries` by `mtfcc`, bypassing
`essentials.districts` entirely — that table reuses geo_ids across layers and is the source
of the collisions the constraint above warns about.

**Files:**
- Create: `backend/migrations/CC_wip_jurisdiction_city_state_nation.sql` (renamed at the end)

**Interfaces:**
- Consumes: nothing
- Produces: `resolve_user_jurisdiction` result gains keys `city` (7-digit place FIPS or
  null), `state` (2-digit state FIPS), `nation` (always `'US'`)

- [ ] **Step 1: Confirm the source rows exist for a known point**

```sql
SELECT mtfcc, geo_id, name
FROM essentials.geofence_boundaries
WHERE ST_Covers(geometry, ST_SetSRID(ST_MakePoint(-96.6989, 33.0198), 4326))
  AND mtfcc IN ('G4000', 'G4110');
```

Expected: `G4000 US United States`, `G4000 48 Texas`, `G4110 4858016 Plano city`.

- [ ] **Step 2: Write the migration**

Append to the existing `v_result` rather than rewriting the function body. Copy the current
definition from `pg_get_functiondef` and add, immediately before `RETURN v_result;`:

```sql
  -- City, state and nation, read straight from the boundary layers by mtfcc.
  --
  -- Deliberately NOT via essentials.districts: that table reuses geo_ids across
  -- layers (48008 is both STATE_UPPER and STATE_LOWER; 48085 is both Collin County
  -- and TX House District 85), so a districts join needs an mtfcc filter anyway and
  -- adds a failure mode for no benefit.
  --
  -- city is null for unincorporated addresses. That is correct and must stay
  -- non-fatal: Arden, NC has no G4110 covering it.
  v_result := v_result || jsonb_build_object(
    'city',   (SELECT gb.geo_id FROM essentials.geofence_boundaries gb
                WHERE gb.mtfcc = 'G4110'
                  AND public.ST_Covers(gb.geometry, v_point)
                ORDER BY gb.geo_id LIMIT 1),
    'state',  (SELECT gb.geo_id FROM essentials.geofence_boundaries gb
                WHERE gb.mtfcc = 'G4000' AND gb.geo_id <> 'US'
                  AND public.ST_Covers(gb.geometry, v_point)
                ORDER BY gb.geo_id LIMIT 1),
    'nation', 'US'
  );
```

- [ ] **Step 3: Dry-run against production, and confirm the rollback reverted**

```bash
psql "$DATABASE_URL" -c "BEGIN; $(cat backend/migrations/CC_wip_jurisdiction_city_state_nation.sql) ROLLBACK;"
```

Then re-run `pg_get_functiondef` and confirm the new keys are **absent** — proving the
rollback actually reverted.

- [ ] **Step 4: Apply, then verify against the two known addresses**

There is no Texas member to test with — every profile today is CA, IN or NC — so verify the
Plano case by point and the NC case by member:


- [ ] **Step 2: Write the migration**

```sql
-- Slice taxonomy: governments, not constituencies.
-- See .planning/research/SLICE-TAXONOMY.md.
--
-- Order matters. Content moves before anything is retired, and the surviving federal
-- slice is chosen as the one already holding posts so the busiest thread never moves.

-- 1. Rename the two mislabelled types. Geoids are already correct for both:
--    `local` holds county FIPS, and the surviving `neighborhood` rows are handled below.
UPDATE civic_spaces.slices SET slice_type = 'county' WHERE slice_type = 'local';

-- 2. Collapse every federal slice (congressional districts) into one nationwide space.
--    The survivor is the slice holding the most posts.
WITH survivor AS (
  SELECT s.id
  FROM civic_spaces.slices s
  LEFT JOIN civic_spaces.posts p ON p.slice_id = s.id
  WHERE s.slice_type = 'federal'
  GROUP BY s.id
  ORDER BY COUNT(p.id) DESC, s.created_at ASC
  LIMIT 1
)
UPDATE civic_spaces.slices
SET geoid = 'US', sibling_index = 1
WHERE id = (SELECT id FROM survivor);

UPDATE civic_spaces.posts p
SET slice_id = (SELECT id FROM civic_spaces.slices WHERE slice_type='federal' AND geoid='US')
WHERE p.slice_id IN (
  SELECT id FROM civic_spaces.slices WHERE slice_type='federal' AND geoid <> 'US'
);

-- Members move only where they are not already in the survivor, or the unique
-- (user_id, slice_id) constraint rejects the update.
UPDATE civic_spaces.slice_members m
SET slice_id = (SELECT id FROM civic_spaces.slices WHERE slice_type='federal' AND geoid='US')
WHERE m.slice_id IN (SELECT id FROM civic_spaces.slices WHERE slice_type='federal' AND geoid <> 'US')
  AND NOT EXISTS (
    SELECT 1 FROM civic_spaces.slice_members m2
    WHERE m2.user_id = m.user_id
      AND m2.slice_id = (SELECT id FROM civic_spaces.slices WHERE slice_type='federal' AND geoid='US')
  );

DELETE FROM civic_spaces.slice_members
WHERE slice_id IN (SELECT id FROM civic_spaces.slices WHERE slice_type='federal' AND geoid <> 'US');
DELETE FROM civic_spaces.slices WHERE slice_type='federal' AND geoid <> 'US';

-- 3. State slices held senate districts (06028, 18040). Collapse to state FIPS,
--    which is the first two characters of the senate-district geoid.
UPDATE civic_spaces.slices SET geoid = LEFT(geoid, 2) WHERE slice_type = 'state';

-- 4. Retire the old neighborhood slices outright. They held school districts and a
--    school-board district, none of which is a city, and they hold no posts. Members
--    are re-derived by re-running assignment in Step 4 of this task.
DELETE FROM civic_spaces.slice_members
WHERE slice_id IN (SELECT id FROM civic_spaces.slices WHERE slice_type = 'neighborhood');
DELETE FROM civic_spaces.slices WHERE slice_type = 'neighborhood';

-- 5. Deduplicate any state slices that collapsed onto the same geoid.
WITH ranked AS (
  SELECT id, geoid, ROW_NUMBER() OVER (PARTITION BY slice_type, geoid ORDER BY created_at) AS rn
  FROM civic_spaces.slices WHERE slice_type = 'state'
),
keeper AS (SELECT geoid, id FROM ranked WHERE rn = 1)
UPDATE civic_spaces.slice_members m
SET slice_id = k.id
FROM ranked r JOIN keeper k ON k.geoid = r.geoid
WHERE m.slice_id = r.id AND r.rn > 1
  AND NOT EXISTS (SELECT 1 FROM civic_spaces.slice_members m2
                  WHERE m2.user_id = m.user_id AND m2.slice_id = k.id);

DELETE FROM civic_spaces.slice_members m
USING (SELECT id FROM civic_spaces.slices s
       WHERE s.slice_type='state'
         AND EXISTS (SELECT 1 FROM civic_spaces.slices o
                     WHERE o.slice_type='state' AND o.geoid=s.geoid AND o.created_at < s.created_at)) dup
WHERE m.slice_id = dup.id;

DELETE FROM civic_spaces.slices s
WHERE s.slice_type='state'
  AND EXISTS (SELECT 1 FROM civic_spaces.slices o
              WHERE o.slice_type='state' AND o.geoid=s.geoid AND o.created_at < s.created_at);

-- 6. Re-reconcile, because the moves above bypass the triggers.
UPDATE civic_spaces.slices s
SET current_member_count = COALESCE(m.n, 0)
FROM (SELECT sl.id, COUNT(sm.user_id) AS n
      FROM civic_spaces.slices sl
      LEFT JOIN civic_spaces.slice_members sm ON sm.slice_id = sl.id
      GROUP BY sl.id) m
WHERE m.id = s.id;

DO $$
DECLARE v_bad integer;
BEGIN
  SELECT COUNT(*) INTO v_bad FROM civic_spaces.slices
  WHERE slice_type IN ('local', 'neighborhood');
  IF v_bad > 0 THEN
    RAISE EXCEPTION 'migration failed: % slices still use a retired slice_type', v_bad;
  END IF;

  SELECT COUNT(*) INTO v_bad FROM civic_spaces.slices
  WHERE slice_type = 'federal' AND geoid <> 'US';
  IF v_bad > 0 THEN
    RAISE EXCEPTION 'migration failed: % federal slices are still districts', v_bad;
  END IF;
END $$;
```
