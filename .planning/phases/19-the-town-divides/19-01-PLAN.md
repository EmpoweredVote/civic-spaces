# Phase 19-01: The split — a full slice divides and the new one opens talking

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When the frontier slice of a jurisdiction reaches 6000 members, it divides: the 3000 most recently joined move to a new sibling, which opens seeded with a forked copy of a recent window of the parent's conversation.

**Architecture:** One `SECURITY DEFINER` function in `civic_spaces` does the whole split in a single transaction — create the sibling, move the members, copy the window. ev-accounts only *decides* that a split should happen and calls it; it cannot touch post content and that wall stays up. Placement inverts in the same change: new members fill the second-newest open slice, not the oldest with room.

**Tech Stack:** Postgres / Supabase migrations (plpgsql); TypeScript + vitest in `ev-accounts`; SQL rehearsal scripts (this repo has no test framework).

**Spec:** `docs/superpowers/specs/2026-11-01-slice-splitting-design.md` — approved 2026-11-01. §4.3, §4.4, §4.5, §5, §5.1, §6, §7, §9.4, §10.

**Depends on:** Phase 18, applied 2026-11-02. Nothing here changes the public RPCs, but §4.9's visitor-landing change is 19-04 and must not be done here by accident.

## Global Constraints

- 🔴 **`slice_members` has no client-writable RLS policy and must not gain one.** The split runs through a `SECURITY DEFINER` function owned by `postgres`. This is the only thing between the schema and a member assigning themselves anywhere.
- 🔴 **ev-accounts must not be granted access to `posts` or `replies`.** Its pool connects as `civic_spaces_app`, which holds DML on `slices`, `slice_members` and `connected_profiles` only — a deliberate privacy property (`ev-accounts` `backend/migrations/CA_0112_civic_spaces_scoped_role.sql`, and the commentary in `config/database.ts`). It gets `EXECUTE` on one function and nothing else.
- **The cap is 6000 and stays 6000.** `enforce_slice_cap()` raises `slice_full` / P0001 at `>= 6000`; `slices_count_max_check CHECK (current_member_count <= 6000)` is a second gate on the table. The split must not raise either; it moves members *out*.
- **The slice types that split are exactly** `('city','county','state','federal','unified')`. `volunteer` does not. 🔴 Declare this as its **own** constant. It equals `PUBLIC_SLICE_TYPES` today by coincidence, not by rule — coupling them would tie a capacity decision to the public-read allowlist (D-28).
- **Every function is `SECURITY DEFINER`, `SET search_path = ''`, every object reference schema-qualified.** An unpinned `search_path` on a definer function is a privilege-escalation hole.
- 🔴 **`joined_at` is carried through a move, never reset.** Stamping `now()` on 3000 rows destroys the only tenure record the platform holds, and it is the key redistribution will sort on.
- **Migrations end with `NOTIFY pgrst, 'reload schema';`** and need 1–2 minutes before a dependent frontend deploys.
- 🔴 **This plan produces reviewed `.sql`, TypeScript and rehearsals. It does not apply DDL to production.** Applying is Chris's call and Chris's hands, through `18-02-APPLY.md`'s discipline: hash the **committed** bytes, never the working tree.
- **Never copy real members' posts into fixtures.** Rehearsal data is wholly synthetic; `scripts/rehearsal/18-02-seed.sql` is the house pattern.

## Review Focus

Input classes the spec implies that no task's assertions would otherwise reach:

1. **A slice that reaches 6000 when a newer sibling already exists.** It must *close*, not split — only the frontier splits (§4.4). A second split here would create a slice nobody fills. Covered in Task 5, Step 1.
2. **A jurisdiction with exactly one slice, reaching 6000.** There is no second-newest to fill, so the open set is a single slice and it is the frontier. Off-by-one in "the two newest" shows up here and nowhere else. Covered in Task 4, Step 1.
3. **A split where the parent holds fewer than 6000 rows because members left.** `current_member_count` is maintained by triggers and can drift from `count(*)`. The mover must take "the 3000 most recent of what is actually there", not assume 6000. Covered in Task 3, Step 1.
4. **Two members with an identical `joined_at`.** The cut is `ORDER BY joined_at DESC LIMIT 3000`; ties make it non-deterministic, so a tiebreaker is required or the same input splits two ways. Covered in Task 3, Step 1.
5. **A seed window containing a post whose author is suspended, or a soft-deleted post or reply.** The feed hides them; the fork must not resurrect them in the new slice. Covered in Task 6, Step 1.

### Task 3: `split_slice()` — the membership move

**Files:**
- Create: `supabase/migrations/20261102000200_split_slice.sql` (section 1 of 2)
- Create: `scripts/rehearsal/19-01-split-members.sql`

**Interfaces:**
- Produces: `civic_spaces.split_slice(p_slice_id uuid, p_seed_window interval DEFAULT interval '14 days') RETURNS uuid`, `SECURITY DEFINER`, `SET search_path = ''`, owned by `postgres`. Returns the new slice's id. Task 6 adds the seed copy to the same body; Task 7 calls it from ev-accounts.

**The membership half, exactly:**

1. `SELECT … FOR UPDATE` on the parent slice row — same lock `enforce_slice_cap()` takes, so a split and a concurrent join serialise.
2. Refuse unless `is_splittable_slice_type(parent.slice_type)`.
3. Refuse unless the parent is the **frontier** — `parent.sibling_index = max(sibling_index)` for its `(slice_type, geoid)`. A non-frontier slice at the cap closes; it does not split (§4.4).
4. Insert the sibling at `max(sibling_index) + 1`.
5. Move the most recently joined half: `ORDER BY joined_at DESC, user_id DESC LIMIT ceil(count(*) / 2.0)`.
6. `NOTIFY pgrst` is **not** needed — no schema change.

🔴 **`count(*)`, not 6000.** Members leave, and `current_member_count` is trigger-maintained and can drift. "The 3000 most recent" means half of what is actually there.

🔴 **`user_id DESC` is the tiebreaker, and it is not decoration.** `joined_at` ties are certain at bulk-assignment time, and without a total order the same input splits two different ways on two runs — which makes the rehearsal non-reproducible and a bug unfindable.

🔴 **An `UPDATE` of `slice_members.slice_id`, not DELETE + INSERT.** The INSERT trigger would re-check the cap and the DELETE trigger would decrement the parent — doing both 3000 times, each taking `FOR UPDATE` on a slice row inside a transaction that already holds one. Update the rows and fix both counts with two statements.

### Task 4: Placement fills the two newest slices

**Files:**
- Modify: `C:\EV-Accounts\backend\src\civic_spaces\services\sliceAssigner.ts` (`findActiveSliceForGeoid`)
- Modify: `C:\EV-Accounts\backend\src\civic_spaces\services\sliceAssigner.test.ts`

**Interfaces:**
- Consumes: nothing from Tasks 1–3.
- Produces: `findActiveSliceForGeoid` unchanged in signature, changed in behaviour. Task 5 depends on it no longer creating empty siblings.

🔴 **This is not a sort reversal.** Today's query is `WHERE current_member_count < 6000 ORDER BY sibling_index ASC LIMIT 1` — the oldest slice with room. The new rule keeps `ASC` and **restricts the candidate set to the two highest `sibling_index` values**, because within the open pair, lowest-first *is* "fill the second-newest first" (§4.3). Reversing the sort instead would fill the newest first and starve the second-newest, which is the opposite of the design.

🔴 **Do not add an `is_closed` column.** "Closed" is not a state a slice is put into — it is the absence of candidacy, and it falls out of this one query: a slice is closed exactly when it is not among the two highest `sibling_index` values for its `(slice_type, geoid)`. A stored flag would be a second source of truth that has to be written at every split, can disagree with `sibling_index`, and would need backfilling for every slice that already exists. The derivation cannot drift because there is nothing to drift from.

### Task 6: `split_slice()` — the seed copy

**Files:**

**The seed half, exactly:**

1. Select the parent's posts with `created_at >= now() - p_seed_window`, `is_deleted = false`, and whose author is not suspended (join `connected_profiles`, `account_standing <> 'suspended'`).
2. Insert copies into the new slice: new `id`, **original `user_id`**, original `title`/`body`, **original `created_at` and `updated_at`**, `forked_from` = the original's id.

## Left to the builder

- The seed window's default duration. The signature takes `p_seed_window interval DEFAULT interval '14 days'`; **14 days is a placeholder, chosen so the parameter has a value, not because it is right.** §7.1 says pick a duration rather than a post count, because a duration degrades sensibly in a quiet jurisdiction. The failure to avoid is a window so long the new slice reads as an archive of somebody else's town.
- How the split is scheduled once ev-accounts has decided on one. 🔴 It cannot run inside `POST /api/civic-spaces/assign` — that pool sets `statement_timeout = 10s` and the frontend calls it fire-and-forget. Nobody is waiting on a split; it needs a queue, a `pg_cron` job, or a deferred call. §9.4 and §10.
- Whether the 3000-row `UPDATE` needs batching to keep the parent's row lock short enough, and what that does to atomicity. A member must never be observably half-moved.
- What a client does when its slice splits underneath it mid-session — in particular a member who is mid-reply.
