# Phase 19-02: Write permissions — standing in a thread, and a door built closed

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A member may write in a slice they belong to, and in any thread they have **already written in** even after a split moved them away — but never in a copy of such a thread, and never in a slice they merely read.

**Architecture:** One SQL predicate decides it, called from the `replies` INSERT policy and projected per row for the UI, so RLS and the interface cannot disagree. The empowered exception is specified and wired but reads a source that does not exist yet, so it is false for everyone — a door built closed, which opens later without reopening this design.

**Tech Stack:** Postgres RLS + plpgsql; TypeScript in `src/lib/writeAccess.ts`; SQL rehearsals and `check:*` guards (no test framework in this repo).

**Spec:** `docs/superpowers/specs/2026-11-01-slice-splitting-design.md` — §4.5, §4.6, §4.7, §4.8, §6, §7.

**Depends on:** **19-01, Task 1** — `posts.forked_from` and `replies.forked_from` must exist, because the central rule here is stated in terms of them. The rest of 19-01 need not be applied.

## Global Constraints

- 🔴 **RLS is the gate; the UI is a courtesy.** Every rule here holds in a policy whether or not the interface agrees. A control the UI forgets to hide must still fail at the database.
- 🔴 **Gate the feed AND the thread.** `CLAUDE.md` records this as a bug that already shipped once: `isViewOnly` must reach `SliceFeedPanel` *and* `ThreadView`, and `ReplyCard` gets `canWrite={canWrite && !isViewOnly}` with no `onReply`. Per-thread standing makes this **per row**, not per panel — strictly harder. Do not ship half of it.
- 🔴 **Never read `connected_profiles.tier`, and never add a tier term to `writeAccess.ts`.** That module says *"There is no `tier` term and there must never be one"*, and `AccountsExplainer.tsx` records that the platform holds **two disagreeing definitions** of tier. Resolving that disagreement inside an RLS policy would settle the platform's identity model by accident, in the worst possible place.
- **Use `civic_spaces.current_user_id()`, never `auth.jwt() ->> 'sub'`.** It resolves `external_id` first, then `sub` — confirmed live over HTTP on 2026-11-02.
- **No new grant to `anon`.** Phase 18's surface is four RPCs and nothing else; nothing here widens it. Re-run `npm run check:anon-read` after any migration and expect 72 PASS / 0 FAIL.
- **Every `SECURITY DEFINER` function pins `SET search_path = ''`** with schema-qualified references.
- 🔴 **Produces reviewed SQL and rehearsals. Does not apply DDL to production.**

## Review Focus

Input classes the spec implies that no task's assertions would otherwise reach:

1. **A fork whose original author is ALSO a member of the new slice** — they were moved there by the same split. They must be able to write, via **membership**, and the fork exclusion must not override that. Getting this wrong silences people in their own slice. Covered in Task 2, Step 1.
2. **A member of a *sibling* slice replying to a thread they never wrote in.** Phase 16 gave them read; this must stay a refusal. The widening is per-thread, not per-jurisdiction. Covered in Task 2, Step 1.
3. **A soft-deleted reply as the basis for standing.** Someone wrote in the thread and then deleted it. `is_deleted` hides the row; it does not un-write it. The predicate must decide deliberately rather than inherit whatever the join does. Covered in Task 1, Step 1 (W8).
4. **The empowered predicate while its source does not exist.** It must return `false`, not error, not `NULL` — a `NULL` in a `WITH CHECK` fails closed by accident rather than by design, which is the right outcome for the wrong reason and will confuse whoever turns it on. Covered in Task 4, Step 1.
5. **An admin placement that would take a slice past 6000.** Two gates stand in the way, not one: `enforce_slice_cap()` **and** the table constraint `slices_count_max_check`. A fix that clears only the trigger fails on the constraint. Covered in Task 5, Step 1.

### Task 1: `has_written_in_thread()` — standing, and the fork exclusion

**Files:**
- Create: `supabase/migrations/20261102000300_thread_standing.sql` (section 1 of 2)
- Create: `scripts/rehearsal/19-02-standing.sql`

**Interfaces:**
- Consumes: `posts.forked_from`, `replies.forked_from` (19-01 Task 1).
- Produces: `civic_spaces.has_written_in_thread(p_viewer text, p_post_id uuid) RETURNS boolean`, `STABLE`, `SECURITY DEFINER`, `SET search_path = ''`. Tasks 2 and 6 call it. 🔴 Revoke from `PUBLIC, anon, authenticated` **in this same file, beside the `CREATE`** — an un-revoked definer function is an RLS-bypassing "who wrote in this thread?" oracle, and since Phase 18 `anon` resolves this schema.

**True when, and only when, the viewer:**
- authored the post, **and `posts.forked_from IS NULL`**; or
- authored any reply in the thread whose **`replies.forked_from IS NULL`**.

🔴 **The fork exclusion is the subtlest rule in this phase, and without it the design inverts.** A seeded copy keeps its original author's `user_id` — that is deliberate, bylines are kept (§4.5). So a naive `posts.user_id = p_viewer` is **true for the fork**, which would hand the original author standing in a slice they were never assigned to, for every seeded thread, at every split. §4.5 says the opposite: *archival — the conversation continues without them.* Standing attaches to the thread you actually wrote in, never to a copy of it (§4.6).

- [ ] **Step 1: Write the failing assertions**

`scripts/rehearsal/19-02-standing.sql`, house style, ending in a CONTROL that must print FAIL. Seed two sibling `city` slices on geoid `9999003`: a parent with a thread (post + 2 replies by different authors), and a child holding a **fork** of that thread.

| # | viewer | thread | expect |
|---|---|---|---|
| W1 | the post's author | the **original** | true |
| W2 | a replier | the **original** | true |
| W3 | someone who never wrote there | the original | false |
| W4 | the post's author | the **fork** | **false** — 🔴 the whole rule |
| W5 | a replier | the **fork** | **false** |
| W6 | someone who wrote only in the fork | the fork | true |
| W7 | someone who wrote only in the fork | the original | false |
| W8 | a replier whose reply is soft-deleted | the original | true (Review Focus 3) |
| W9 | `NULL` viewer | any | false |
| C | CONTROL | | must print FAIL |

🔴 **W8 is a decision, not a discovery.** Deleting your words hides them; it does not un-write them, and a thread you were part of does not stop being one. State that in the function's `COMMENT`, so the next reader knows it was chosen.

🔴 **W7 is the mirror of W4** and exists because W4 alone passes on a function that returns false for *every* fork question, including W6.

- [ ] **Step 2: Run it against a scratch DB and verify it fails**

Scratch per `18-02-APPLY.md`'s recipe.
Expected: all FAIL — `function has_written_in_thread does not exist`.

- [ ] **Step 3: Implement**

Two `EXISTS` arms, both carrying `forked_from IS NULL`. `COMMENT ON FUNCTION` stating the rule, the W8 decision, and why the fork exclusion exists.

- [ ] **Step 4: Run it and verify it passes**

Expected: W1–W9 PASS, C FAIL.

- [ ] **Step 5: Mutation-prove the fork exclusion**

🔴 Required. Drop `AND forked_from IS NULL` from both arms inside a transaction; confirm **W4, W5 and W7 flip to FAIL while W1, W2, W3 and W6 stay PASS**. Roll back.
Verify the edit landed before reading the result — a mutation that silently did not apply reports a clean pass and reads exactly like a blind guard.

- [ ] **Step 6: Commit**

```bash
git add supabase/migrations/20261102000300_thread_standing.sql scripts/rehearsal/19-02-standing.sql
git commit -m "feat(write): standing attaches to the thread you wrote in, never to a copy"
```

### Task 2: The `replies` INSERT policy widens to standing

**Files:**
- Modify: `supabase/migrations/20261102000300_thread_standing.sql` (section 2 of 2)
- Create: `scripts/rehearsal/19-02-reply-policy.sql`

**Interfaces:**
- Consumes: `has_written_in_thread`.
- Produces: `replies_insert_slice_member` replaced by `replies_insert_member_or_standing`.

**The policy:** `user_id = current_user_id()` AND ( the post's slice is one of mine **OR** `has_written_in_thread(current_user_id(), post_id)` ).

🔴 **`posts` INSERT is NOT widened.** Standing is permission to continue a conversation, not to start one somewhere you do not belong. `posts_insert_slice_member` stays exactly as it is.

🔴 **Drop the old policy in the same statement block as the new one.** Postgres ORs permissive policies together, so leaving both would be harmless *here* — but the next person to read `pg_policies` would see two overlapping INSERT rules and have to work out which governs.

- [ ] **Step 1: Write the failing assertions**

`scripts/rehearsal/19-02-reply-policy.sql`. Real inserts under `SET LOCAL ROLE authenticated` + `SET LOCAL request.jwt.claims`, each wrapped so a refusal is caught and reported (`42501` is the expected code).

| # | viewer | target | expect |
|---|---|---|---|
| R1 | a member of the post's slice | that thread | INSERT succeeds — the control case |
| R2 | a non-member with standing (wrote there before the split) | that thread | **succeeds** — §4.6 backward |
| R3 | a non-member of a **sibling** slice, no standing | that thread | refused `42501` (Review Focus 2) |
| R4 | the fork's original author | the **fork** | refused `42501` — §4.5 forward |
| R5 | the fork's original author who is **also a member** of the new slice | the fork | **succeeds**, via membership (Review Focus 1) |
| R6 | anyone | a thread in another **jurisdiction** | refused |
| R7 | a member | a **post** INSERT in a slice they only read | refused — posts did not widen |
| R8 | `anon` | anything | refused |

Membership must win. A policy written as `standing AND NOT forked` instead of `membership OR standing` fails exactly here.

### Task 3: A fork is not its author's to revise

**Files:**
- Create: `supabase/migrations/20261102000400_fork_is_archival.sql`
- Create: `scripts/rehearsal/19-02-fork-archival.sql`

**Interfaces:**
- Produces: `posts_update_own` and `replies_update_own` replaced by versions carrying `AND forked_from IS NULL`.

🔴 **Today's `posts_update_own` is `user_id = current_user_id()` with no slice term at all.** The fork carries the original author's `user_id`, so without this an author can silently rewrite a fork — in a slice they have no standing in, after people there have replied to it.

**Deletion and moderation propagate; editing does not.** The asymmetry is reasoned in §4.5: editing is an attempt to change a conversation you are not in, whereas deletion withdraws consent to publish those words at all, and that consent was never slice-scoped.

- [ ] **Step 1: Write the failing assertions**

| # | claim |
|---|---|
| A1 | the original author UPDATEs their **original** post — succeeds |
| A2 | the original author UPDATEs the **fork** — refused `42501` |
| A3 | the original author UPDATEs a **reply fork** — refused |
| A4 | soft-deleting the original sets `is_deleted` on the fork too |
| A5 | a moderator removing the original removes the fork |
| A6 | soft-deleting the **fork** leaves the original untouched — propagation is one-way |
| A7 | a member of the fork's slice who wrote a **non-fork** reply there can still edit that reply |
| C | CONTROL, must print FAIL |

🔴 A7 guards against over-reaching: the rule is about *forked rows*, not about the slice they live in. A6 pins the direction, which a trigger written symmetrically would get wrong.

- [ ] **Step 2: Run it and verify it fails**

Expected: A2, A3, A4, A5 FAIL.

- [ ] **Step 3: Implement**

Policies for A2/A3. For A4/A5, an `AFTER UPDATE` trigger on `posts` and `replies` that, when `is_deleted` flips false → true on a row with `forked_from IS NULL`, sets `is_deleted` on rows whose `forked_from` is that row. 🔴 Guard against recursion: the trigger must not re-fire on the rows it just updated (`WHEN (OLD.is_deleted IS DISTINCT FROM NEW.is_deleted)` plus a `forked_from IS NULL` condition on the firing row).

- [ ] **Step 4: Run it and verify it passes**

Expected: A1–A7 PASS, C FAIL.

- [ ] **Step 5: Commit**

```bash
git add supabase/migrations/20261102000400_fork_is_archival.sql scripts/rehearsal/19-02-fork-archival.sql
git commit -m "feat(write): a fork is archival — not editable, and it follows its original into deletion"
```

### Task 4: The empowered exception, built closed

**Files:**
- Create: `supabase/migrations/20261102000500_empowered_write.sql`
- Create: `scripts/rehearsal/19-02-empowered.sql`

**Interfaces:**
- Produces: `civic_spaces.is_empowered_writer(p_viewer text, p_slice_id uuid) RETURNS boolean`, `STABLE`, `SECURITY DEFINER`, revoked from `PUBLIC, anon, authenticated` beside its `CREATE`. Task 2's policy gains a third `OR` arm calling it.

**It returns `false` for everyone.** Empowered accounts do not exist in the code; Chris confirmed on 2026-11-01 that they will be their own profile alongside `connected_profiles` — for civic leaders and people who make an impact through Empowered features, who propose solutions and speak publicly, and who trade privacy for transparency. Deliberately not most people.

**Scope, when it does exist:** any sibling slice of a jurisdiction the account **belongs to** — every slice of their own city, their own county, their own state. **Not platform-wide.** A civic leader needs to reach all of their city's slices; nobody needs to post into a city they have no standing in, and a single misused platform-wide account could.

🔴 **The body must `RETURN false` explicitly, not query a table that does not exist** (which fails to create) **and not return `NULL`** (which fails closed by accident rather than by design, and will mislead whoever turns it on). Write the real shape in the `COMMENT` so the later author has the specification in front of them.

### Task 5: The admin override, past both gates

**Files:**
- Create: `supabase/migrations/20261102000600_admin_placement.sql`
- Create: `scripts/rehearsal/19-02-admin-override.sql`

**Interfaces:**
- Produces: `civic_spaces.admin_place_member(p_user_id text, p_slice_id uuid) RETURNS void`, `SECURITY DEFINER`, granted `EXECUTE` to `civic_spaces_app` only.

**Two gates, not one.** `enforce_slice_cap()` raises at `>= 6000`, **and** `slices_count_max_check CHECK (current_member_count <= 6000)` sits on the table. Raise the constraint's ceiling to **6100** and have the override refuse above it; the trigger goes on enforcing 6000 for every self-serve placement, so the normal path is untouched.

🔴 **6100 is deliberately arbitrary and deliberately small** — large enough for the spouse case many times over, small enough that a bug in the override surfaces as a refusal rather than an unbounded slice.

🔴 **Not the `moderators` table.** `civic_spaces.moderators` / `is_moderator()` is a *content* role — removing posts, acting on reports. Placing a person into a community is a different power. Platform roles live in ev-accounts, and `checkVolunteerRole` (`getCachedUserRoles` + `checkRole`) is the pattern to follow; this repo must not grow a second role system.

- [ ] **Step 1: Write the failing assertions**

| # | claim |
|---|---|
| D1 | places a member into a **closed** slice that is below 6000 |
| D2 | places a member into a slice **at** 6000 — past both gates (Review Focus 5) |
| D3 | refuses at 6100 with a named error, not a constraint violation |
| D4 | `slices_count_max_check` now permits 6100 and still refuses 6101 |
| D5 | `enforce_slice_cap()` still raises `slice_full` at 6000 on an **ordinary** insert — the normal path is unchanged |
| D6 | `current_member_count` stays equal to `count(*)` after an override |
| D7 | it is **not** executable by `anon` or `authenticated` |
| D8 | it does **not** call `is_moderator()` — grep the file |
| C | CONTROL, must print FAIL |

🔴 **D5 is the one that keeps this honest.** It is easy to raise a ceiling and quietly raise it for everybody; D5 fails if the override's headroom leaks into ordinary joins.

- [ ] **Step 2: Run it and verify it fails**

Expected: D1–D8 FAIL.

- [ ] **Step 3: Implement**

`ALTER TABLE … DROP CONSTRAINT slices_count_max_check, ADD CONSTRAINT … CHECK (current_member_count <= 6100)`, then the function: lock the slice row, refuse above 6100 with `RAISE EXCEPTION … USING ERRCODE = 'P0001'`, insert the membership with the cap trigger disabled for this path, and fix the count. Record in the comment that the ceiling is two numbers — 6000 for self-serve, 6100 absolute — and why.

- [ ] **Step 4: Run it and verify it passes**

Expected: D1–D8 PASS, C FAIL. Re-run Task 2's rehearsal and `check:anon-read`.

**The three states (§4.7):**

| state | appearance |
|---|---|
| `own-slice` | normal, full reply affordance |
| `standing` | slice tag, reply live, composer says you are posting into a different slice |
| `read-only` | slice tag, **no reply affordance at all** |

🔴 **The rule is *no standing means read-only*, not *different slice means read-only*.** A row in another slice with standing is writable, and a design that collapses the middle state loses the exception this phase exists to build.

🔴 **69 is the important one.** `rowWriteState` must take `may_reply` as an input, not re-derive standing from slice ids it happens to have — a second implementation of the rule is the drift this phase is trying to prevent, and the one in RLS is the one that counts.

## Left to the builder

- Whether `may_reply` is a column on the feed projection, a separate RPC, or a policy-side function. This plan requires only that there is **one** source and the UI does not re-derive it. §10.
- The index behind `has_written_in_thread`. `replies` is indexed on `(post_id, created_at)`, **not on `user_id`**, and the predicate runs per row over a paginated feed. Measure before adding one; a partial index on `(post_id, user_id) WHERE forked_from IS NULL` is the obvious candidate.
- How the admin override is invoked and audited end to end — who calls `admin_place_member`, and what record it leaves.
- The copy for the `standing` composer. It has to say "you are posting into a different slice" in the product's voice, and nothing in this repo says it yet.
