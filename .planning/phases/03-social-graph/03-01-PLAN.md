**3. Friendships table (single-row normalized):**
- Columns: user_low (text NOT NULL), user_high (text NOT NULL), status (text NOT NULL), created_at (timestamptz DEFAULT now()), updated_at (timestamptz DEFAULT now())

- CHECK (user_low < user_high)
- CHECK (status IN ('REQ_LOW', 'REQ_HIGH', 'FRIEND'))
- Indexes: idx_friendships_user_low_status (user_low, status), idx_friendships_user_high_status (user_high, status)
- GRANT SELECT, INSERT, UPDATE, DELETE ON civic_spaces.friendships TO authenticated

**4. Follows table (directional):**
- Columns: follower_id (text NOT NULL), target_id (text NOT NULL), created_at (timestamptz DEFAULT now())
- PRIMARY KEY (follower_id, target_id)
- Indexes: idx_follows_follower (follower_id), idx_follows_target (target_id)
- GRANT SELECT, INSERT, DELETE ON civic_spaces.follows TO authenticated

**5. RLS on friendships — CRITICAL: every policy must use (select civic_spaces.current_user_id()) wrapping and cover BOTH user_low and user_high sides:**

- Enable RLS: `ALTER TABLE civic_spaces.friendships ENABLE ROW LEVEL SECURITY;`
- SELECT policy "friendships_select_own": USING with OR on both user_low and user_high
- INSERT policy "friendships_insert_own": WITH CHECK ensures requester is part of the pair AND status matches their side (user_low + REQ_LOW, or user_high + REQ_HIGH)
- UPDATE policy "friendships_update_accept": USING restricts to recipient only (REQ_LOW means user_high can accept; REQ_HIGH means user_low can accept). WITH CHECK restricts new status to 'FRIEND' only.
- DELETE policy "friendships_delete_own": USING with OR on both sides (either party can remove/cancel)

Copy the exact RLS SQL from 03-RESEARCH.md Pattern 3.

- Enable RLS: `ALTER TABLE civic_spaces.follows ENABLE ROW LEVEL SECURITY;`

- INSERT policy: follower_id = current user AND target_id must be in connected_profiles WHERE tier = 'empowered' (subquery enforces Empowered-only)
- DELETE policy: follower_id = current user

Copy the exact RLS SQL from 03-RESEARCH.md Pattern 4.
