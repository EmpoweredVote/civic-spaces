# Phase 18-01: Reconcile the `public.*` grant surface

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the undocumented `public.*` views into git and revoke the `anon` privileges nothing asked for, so that Phase 18-02 opens exactly one door instead of two.

**Architecture:** One migration that (a) re-declares the five Civic Spaces views that exist in production but in no migration, with their current definitions, and (b) `REVOKE`s all `anon` privileges on the twelve views this app owns. One new guard, `check:grants`, that diffs the live catalog against a committed expectation so the next drift is caught rather than discovered. **No behaviour changes** — the views already return nothing to `anon` — which is what makes this safe to ship alone and ahead of everything else.

**Tech Stack:** Postgres / Supabase migrations; Node 22 `--experimental-strip-types` for the guard; `@supabase/supabase-js` with an anon key for the HTTP half.

**Spec:** `.planning/phases/18-the-public-square/18-CONTEXT.md` — D-43 is this plan in its entirety.

## Global Constraints

- **This plan changes no application behaviour.** Every view it touches already returns zero rows to `anon`. If any verification step shows a row count changing for `authenticated`, stop.
- **`public.users_public` is out of scope and must not be modified.** It reads a `users` table Civic Spaces does not own (verified 2026-10-30), so at least one other EV app shares this schema. Document it; do not touch its definition or its grants.
- Migrations end with `NOTIFY pgrst, 'reload schema';` and need 1–2 minutes before a dependent frontend deploys.
- DDL goes through the `supabase-local` MCP, which is the only DDL path in this project.
- 🔴 **This plan produces a reviewed `.sql` file and verification output. It does not apply DDL to production.** Applying is Chris's call and Chris's hands.
- The twelve views this app owns: `posts`, `replies`, `slices`, `slice_members`, `connected_profiles` (the five untracked) and `friendships`, `follows`, `civic_notifications`, `flags`, `blocks`, `moderators`, `action_log` (the seven the migrations create).

## Review Focus

Input classes the spec implies that no task's assertions would otherwise reach:

1. **A view added to `public` after this plan ships** inherits Supabase's default privileges and hands `anon` everything again. The guard must fail on an *unknown* view, not only on a known one with wrong grants — a denylist here repeats D-28's mistake. Covered in Task 2, Step 1.
2. **`REVOKE` on a view `authenticated` also reads.** Revoking from `anon` must not cascade or otherwise disturb `authenticated`'s grants. Covered in Task 3, Step 4.
3. **A view whose production definition differs from what the migration declares.** `CREATE OR REPLACE VIEW` with a different column list errors rather than replacing; with the same list it silently succeeds. The baseline fixture is what tells the two apart. Covered in Task 1.
4. **The guard run against a project with no `civic_spaces` schema** (a fresh clone, a reviewer's sandbox) must say so and exit non-zero rather than reporting a clean surface. A guard that passes vacuously is the failure mode `check-explore-gate` was already bitten by. Covered in Task 2, Step 5.
5. **`anon` holds `INSERT`/`UPDATE`/`DELETE`, not just `SELECT`,** on all twelve. A revoke that handles only `SELECT` leaves a pre-granted write surface for any future permissive INSERT policy. Covered in Task 3, Step 1.

### Task 1: Capture the catalog baseline as a committed fixture

**Files:**
- Create: `scripts/fixtures/grant-surface.json`
- Create: `.planning/phases/18-the-public-square/18-01-BASELINE.md`

**Interfaces:**
- Produces: `scripts/fixtures/grant-surface.json` — the expectation `check:grants` (Task 2) diffs against. Shape: `{ "views": { "<name>": { "owner": string, "securityInvoker": boolean, "columns": string[], "grants": { "anon": string[], "authenticated": string[] } } }, "ownedByUs": string[], "foreign": string[] }`.

- [ ] **Step 1: Run the catalog query and save its raw output**

Run, via the `supabase-local` MCP `execute_sql`:

```sql
SELECT c.relname AS view_name,
       pg_get_userbyid(c.relowner) AS owner,
       COALESCE((SELECT option_value FROM pg_options_to_table(c.reloptions)
                 WHERE option_name = 'security_invoker'), 'off') AS security_invoker,
       (SELECT array_agg(a.attname ORDER BY a.attnum)
          FROM pg_attribute a WHERE a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped) AS columns,
       (SELECT array_agg(DISTINCT tp.privilege_type ORDER BY tp.privilege_type)
          FROM information_schema.table_privileges tp
         WHERE tp.table_schema = 'public' AND tp.table_name = c.relname AND tp.grantee = 'anon') AS anon_privs,
       (SELECT array_agg(DISTINCT tp.privilege_type ORDER BY tp.privilege_type)
          FROM information_schema.table_privileges tp
         WHERE tp.table_schema = 'public' AND tp.table_name = c.relname AND tp.grantee = 'authenticated') AS auth_privs
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'v'
ORDER BY c.relname;
```

Expected at the time of writing: 15 rows; `security_invoker = on` for all but `geography_columns` and `geometry_columns` (owned by `supabase_admin`, PostGIS, foreign); `anon_privs` containing all of `DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE` on the twelve we own.

`ownedByUs` is the twelve named in Global Constraints. `foreign` is `users_public`, `geography_columns`, `geometry_columns`. Record the grants **as they are today**, not as they should be — Task 3 is what changes them, and Task 2's guard must go red against this fixture before it goes green.

- [ ] **Step 3: Record the definitions of the five untracked views**

Run `SELECT viewname, definition FROM pg_views WHERE schemaname='public' AND viewname IN ('posts','replies','slices','slice_members','connected_profiles');` and paste the verbatim output into `18-01-BASELINE.md`, with the date and the project ref. 🔴 Task 3's migration must reproduce these column lists exactly; `CREATE OR REPLACE VIEW` cannot change a column list and will error if they differ.

### Task 2: The `check:grants` guard

**Files:**
- Create: `scripts/check-grant-surface.mjs`
- Modify: `package.json` (add `"check:grants": "node scripts/check-grant-surface.mjs"`)

**Interfaces:**
- Consumes: `scripts/fixtures/grant-surface.json` from Task 1.
- Produces: `npm run check:grants`, exit 0 on a clean surface and non-zero otherwise, printing one `PASS`/`FAIL` line per assertion in the style of `scripts/check-write-access.mjs`.

- [ ] **Step 1: Write the failing assertions**

Four assertion families, run against the live catalog using the same query as Task 1 Step 1 through a service-role connection:

```js
// 1. No unknown view. An UNRECOGNISED view is a failure, not a pass —
//    Supabase's default privileges hand anon everything on anything new.
check('every public view is either ours or a known foreign one',
  liveViews.every((v) => fixture.ownedByUs.includes(v.name) || fixture.foreign.includes(v.name)))

// 2. anon holds NOTHING on anything we own.
check('anon holds no privilege on any view this app owns',
  fixture.ownedByUs.every((n) => (live[n]?.grants.anon ?? []).length === 0))

// 3. security_invoker stays on. Turning it off silently bypasses RLS.
check('security_invoker is on for every view this app owns',
  fixture.ownedByUs.every((n) => live[n]?.securityInvoker === true))

// 4. Column lists have not drifted from the baseline.
check('no view this app owns has gained or lost a column',
  fixture.ownedByUs.every((n) =>
    JSON.stringify(live[n]?.columns) === JSON.stringify(fixture.views[n].columns)))
```

- [ ] **Step 2: Run it and verify assertion 2 FAILS**

Run: `npm run check:grants`
Expected: assertions 1, 3 and 4 PASS; assertion 2 **FAILS**, naming all twelve views. This is the drift Task 3 fixes, and seeing it red here is what proves the guard can see it at all.

- [ ] **Step 3: Add the HTTP half**

A second section that, using `SUPABASE_URL` and the **anon** key, issues `GET /rest/v1/<name>?select=*&limit=1` for each of the twelve and asserts HTTP 401/403/404 or an empty array — never a row. 🔴 The catalog half and the HTTP half are not redundant: the catalog proves the grant is gone, the HTTP half proves PostgREST agrees, and only the second one reflects the schema cache.

- [ ] **Step 4: Run it and verify the HTTP half passes today**

Run: `npm run check:grants`
Expected: every HTTP assertion PASSES even now — `anon` has the grant but no RLS policy and no `civic_spaces` `USAGE`, so the rows do not come back. A failure here before Task 3 means there is a live exposure and the plan stops.

- [ ] **Step 5: Make a missing schema loud**

If the catalog query returns zero rows, or `SUPABASE_URL` is unset, print `SKIP — no reachable project; this guard proves nothing` and exit **non-zero**. A vacuous pass is the failure `check-explore-gate`'s control case exists to prevent.

- [ ] **Step 6: Commit**

```bash
git add scripts/check-grant-surface.mjs package.json
git commit -m "test(grants): check:grants diffs the live public.* surface against the baseline"
```

### Task 3: The reconciliation migration

**Files:**
- Create: `supabase/migrations/20261030000000_reconcile_public_views.sql`
- Modify: `scripts/fixtures/grant-surface.json` (anon grants become `[]`)

**Interfaces:**
- Consumes: the verbatim definitions recorded in `18-01-BASELINE.md` (Task 1, Step 3).
- Produces: a reviewed migration file. **Not applied by this plan.**

- [ ] **Step 1: Write the migration**

Three sections, in this order, with a header comment explaining that these views existed in production and in no migration, and that `anon`'s privileges came from Supabase's default privileges on `public` rather than from any `GRANT` in this repo.

1. `CREATE OR REPLACE VIEW public.<name> AS SELECT <exact column list> FROM civic_spaces.<name>;` for the five untracked views, with `WITH (security_invoker = on)` stated explicitly rather than inherited.
2. `REVOKE ALL ON public.<name> FROM anon;` for all twelve. 🔴 `ALL`, not `SELECT` — `anon` holds `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` and `TRIGGER` too, and a future permissive INSERT policy would find them waiting.
3. `NOTIFY pgrst, 'reload schema';`

Add a comment naming `public.users_public` and saying explicitly that it is deliberately untouched, with the reason.

- [ ] **Step 2: Rehearse it in a transaction and verify the five replacements succeed**

Through the `supabase-local` MCP, run the migration body inside `BEGIN; … ROLLBACK;`.
Expected: no error. An error on a `CREATE OR REPLACE VIEW` means the recorded column list does not match production — go back to Task 1, Step 3 rather than editing the column list to fit.

- [ ] **Step 3: Rehearse the revoke and verify anon reaches zero**

In the same rolled-back transaction, re-run Task 1's catalog query.
Expected: `anon_privs` is NULL or empty for all twelve; the three foreign views are unchanged.

- [ ] **Step 4: Verify `authenticated` is untouched**

In the same transaction, assert `auth_privs` for all twelve matches the baseline fixture exactly.
Expected: identical. 🔴 This is the assertion that proves the plan's "no behaviour change" claim; without it the claim is an intention.

- [ ] **Step 5: Update the fixture to the post-migration expectation**

Set `grants.anon` to `[]` for all twelve in `scripts/fixtures/grant-surface.json`. `npm run check:grants` now fails against *production* and will pass once the migration is applied — which is the correct state for a plan that does not apply its own DDL.

- [ ] **Step 6: Commit**

```bash
git add supabase/migrations/20261030000000_reconcile_public_views.sql scripts/fixtures/grant-surface.json
git commit -m "fix(grants): track the five untracked public views and revoke anon's privileges"
```
