# Phase 16-04 — Explore follows the active tab, and drafts re-key to `(sliceType, geoid, topicId)`

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the State tab show State's Explore — without ever letting a question written
on one tab post to another jurisdiction.

**Architecture:** Two changes that must land in this order, in this plan, and nowhere else.
First the storage re-key: a draft is identified by `(sliceType, geoid, topicId)` instead of a
bare topic id, loses its `sliceId` / `tab` / `communityName` fields, and derives its
destination at post time through `canPostDraft` — the pure guard 16-01 built. Only then does
`ActiveExplore` stop binding to `homeSlice` and start re-keying on `slices[activeTab]`. The
order is not stylistic: the moment a generic topic can appear on two tabs, one key with one
binding is the exact path by which a federal question reaches a city feed, and that is one of
this phase's four anti-goals.

**Tech Stack:** React 19 · TypeScript 5.7 · Vite 6 · TanStack Query · `localStorage` · no
test framework (see `16-SHARED.md`).

**Spec:** `16-DESIGN.md` (decision 4, and "Settled in review" — drafts re-keyed, no geoid
means the generic composition, a Unified-only member may post to Unified), `16-CONTEXT.md`
(locked decision 3; "Settled after research" item 3), `16-RESEARCH.md` **Finding 4** — read
Finding 4 before Task 1; it lists every call site, with line numbers.

**Depends on:** 16-03. **Execute serially after it** — see the plan-set table in 16-01.

**Carries:** locked decision 3; DESIGN decision 4; DESIGN "Settled in review" items 1, 3, 4,
5; research Finding 4; Pitfalls 5, 6, 11.

### Task 1: Re-key the storage

`cs_explore_drafts` is `Partial<Record<TopicId, ExploreDraft>>` — one draft per topic, for
the whole app — and `cs_explore_resume` is a **bare topic-id string**. Both are two days old
(Explore shipped 2026-10-22), both are per-browser, and the design says drop rather than
migrate: a migration for a two-day-old key costs more than it saves.

**Files:**
- Modify: `src/components/explore/exploreStorage.ts:19-46, 68-95, 107-122`
- Reference (do not edit): `src/hooks/useAllSlices.ts:7-10, 43-55` — `slices` is
  `Partial<Record<SliceType, SliceInfo>>`, i.e. **at most one slice per type**, which is the
  fact that lets the draft drop its `sliceId`

- [ ] **Step 1: Narrow `ExploreDraft`**

```ts
/**
 * One per (sliceType, geoid, topicId) — see draftKey() in lib/exploreComposition.ts.
 *
 * sliceId, tab and communityName are GONE. They existed to pin a draft to one
 * community, which the key now does better: a member holds at most one slice per
 * type, so the destination is derived at post time by canPostDraft(), which also
 * refuses a draft whose geoid no longer matches. That retires the `movedFrom`
 * machinery in ExploreView — a draft for a place the member has left no longer
 * needs a rescue path, because its key matches no slice they hold and it is
 * simply never offered.
 */
export interface ExploreDraft {
  title: string
  body: string
  updatedAt: number
}

export type DraftMap = Record<string, ExploreDraft>
```

- [ ] **Step 2: New key names, and delete the old ones once**

```ts
const DRAFTS_KEY = 'cs_explore_drafts_v2'
const RESUME_KEY = 'cs_explore_resume_v2'
const LEGACY_KEYS = ['cs_explore_drafts', 'cs_explore_resume']
```

🔴 New names are not cosmetic. `read()` is an unchecked `JSON.parse(...) as T` (`:48-55`):
reusing `cs_explore_resume` would make `readResume()` return the old bare string where an
object is now expected, and it would not throw — it would be silently mis-typed and then
used as a key. Delete the two legacy keys on first load, once, in a module-level side effect
inside the same `try/catch` the rest of the file uses.

`cs_explore_ui` keeps its name (16-03 shape-guarded `openTopic`). `cs_saved_adventures` keeps
its name — a device bookmark, unaffected.

- [ ] **Step 3: The resume marker carries the whole key**

```ts
/**
 * "Post this after sign-in", set when a signed-out visitor presses Join.
 *
 * It carries the full draft key, not a topic id: a generic topic can now appear
 * on two tabs, and a bare id cannot say which one they meant.
 *
 * geoid is null for a signed-out visitor — they have no slice yet. Task 3
 * re-keys null-geoid drafts to the member's own slice on sign-in, so by the time
 * this marker is consumed the draft is already where it belongs.
 */
export interface ExploreResume {
  sliceType: string
  geoid: string | null
  topicId: string
  at: number
}
```

- [ ] **Step 4: Keep the new API alongside the old, for one commit**

`ExploreView` and `AppShell` still call `readDrafts()` / `writeDraft(topicId, …)` /
`readResume()` with the old shapes. Export the new functions under the new names
(`readDrafts`, `writeDraft` taking a key, `readResume` returning `ExploreResume`) **and keep
the old signatures exported and working against the legacy in-memory shape** until Task 2
moves every consumer and deletes them in one commit.

That is a strangler, not duplication-for-its-own-sake: it is what keeps this commit green.
`noUnusedLocals` does not flag an unused *export*, so nothing fights you.

### Task 2: `ExploreView` consumes the new key

About a dozen sites. Research Finding 4 lists them with line numbers; work down that list
rather than chasing compiler errors, or the two that are not type errors will be missed.

**Files:**
- Modify: `src/components/explore/ExploreView.tsx` — `:87-88` (hooks), `:90-101`
  (`draftFor`), `:105-119` (`saveDraft`), `:121-128` (`startConversation`), `:145-163` (the
  resume effect), `:174-186` (`onChange` / `onRebind` / `onDiscard`), `:350-351`
  (`movedFrom`), `:442-450` (the moved-from banner), `:469` (`hasDraft`)
- Modify: `src/components/explore/exploreStorage.ts` — delete the legacy signatures

- [ ] **Step 1: Key inside the context, not at every call site**

Modules keep calling `ctx.draftFor(topicId)`. `ExploreView` builds the key from `composition`
plus the topic id, so no module ever sees a key and no module can build a wrong one. This is
the single most valuable line in the plan:

```ts
const keyFor = useCallback(
  (topicId: string) => draftKey(sliceType, geoid, topicId),
  [sliceType, geoid],
)
```

`draftFor` defaults the title from the resolved topic's `suggestedTitle` — look it up in
`topicsById`, not in the deleted `TOPICS`.

- [ ] **Step 2: `saveDraft` loses its binding step**

`:105-119` currently computes `bind = !current.sliceId && destination` and stamps three
fields on first save. All of it goes. A draft is `{title, body, updatedAt}`; where it posts
is decided by its key at post time. Fewer moving parts, and the one that could go wrong is
gone.

- [ ] **Step 3: Delete `movedFrom` and the rebind path**

`:350-351` compares `draft.sliceId` to `destination.sliceId`; `:442-450` renders an amber
"This draft was started for X… Post it in Y instead" banner with a rebind button. Both are
now unreachable and both are deleted, along with `onRebind` (`:175-184`) and the
`disabled={!!movedFrom || …}` half of the submit button (`:466`).

What replaces them is better: a draft whose key does not match a slice the member currently
holds is **never surfaced**, because `draftFor` only ever builds a key from the composition
being rendered. There is nothing to rescue and nothing to explain. Keep the `disabled` when
`isAuthenticated && !destination` — that case is real.

Deleting a control that re-points a draft at another community also removes write affordance
#8 from Research Finding 5's table, which is one fewer thing for 16-05 to gate.

- [ ] **Step 4: The resume effect**

`:145-163`. Three changes:

- `readResume()` returns `ExploreResume | null`. Age it out at 24 h as today
  (`RESUME_MAX_AGE_MS`, `:28`) — a marker older than that was left by someone who signed in
  without an address, so `ExploreView` never mounted to consume it.
- Rebuild the draft key from the marker, not from a bare topic id.
- Run it through `canPostDraft` before calling `startConversation`. `ok: false` means drop
  the marker and leave the draft where it is — silently. Losing a draft a member wrote for a
  place they have left is better than posting it somewhere they did not mean.

🔴 This effect reaches the composer **with no button press**, and it fires once on mount
(`resumedRef`, `:144`). Both facts matter in 16-05; note them, do not act on them here.

- [ ] **Step 5: Delete the legacy storage signatures**

Every consumer has moved. Remove the old `readDrafts` / `writeDraft` / `readResume` /
`writeResume` shapes from `exploreStorage.ts` in **this** commit, so the strangler does not
outlive its purpose.

### Task 3: Re-key a signed-out draft when the member signs in

🔴 **The gap this closes.** A visitor types a draft while signed out; it is stored at
`city||<topicId>` (no geoid). They then sign in **from the header**, not by pressing Join —
so no resume marker exists. `draftFor` now builds `city|<geoid>|<topicId>`, which is a
different key, and the draft they typed is invisible forever. The resume path (Task 2) only
covers the member who pressed Join.

`16-CONTEXT.md` "Settled after research" item 3 is explicit: a signed-out draft *"binds to
the member's own most-local slice on sign-in"*. That binding has to happen on sign-in, not
only on resume.

**Files:**
- Modify: `src/lib/exploreComposition.ts` (the pure half)
- Modify: `src/components/explore/ExploreView.tsx` (the one-time pass)
- Modify: `scripts/check-composition.mjs`

- [ ] **Step 1: The pure function**

```ts
/**
 * Re-keys drafts written while signed out onto the slices the member actually
 * holds, once, after sign-in.
 *
 * A signed-out draft has an empty geoid segment (`city||topic`). On sign-in the
 * member has a real city slice, so the draft moves to `city|<geoid>|topic` —
 * which is what every reader will look for from then on.
 *
 * Rules:
 *  - A key with a non-null geoid is left alone. It is already bound.
 *  - A placeless key (`federal|topic`) is left alone. It has no geoid segment.
 *  - A null-geoid key whose type the member has NO slice for is left alone,
 *    not deleted: they may be assigned that slice later, and a draft is cheap.
 *  - If the destination key already exists, the NEWER updatedAt wins, and the
 *    other is dropped. Two drafts for one topic in one place is not a state the
 *    UI can show.
 */
export function migrateSignedOutDrafts(
  drafts: Record<string, { updatedAt: number }>,
  slices: Partial<Record<string, { geoid: string } | undefined>>,
): { next: Record<string, unknown>; changed: boolean }
```

Return `changed` so the caller can skip the write when there is nothing to do — this runs on
every authenticated mount and must be free in the common case.

- [ ] **Step 2: Run it once, after sign-in**

In `ExploreView`, beside the resume effect and **before** it — guarded by its own ref so it
runs once per mount, and only when `isAuthenticated` and `slices` have resolved. Order
matters: the resume marker's key must be looked up *after* the draft has moved, or resume
reads the old key and finds nothing.

- [ ] **Step 3: Add the checks**

In `scripts/check-composition.mjs`:

| # | Check | Expected |
|---|---|---|
| 42 | `city\|\|t` with a city slice at `1805860` | becomes `city\|1805860\|t`; `changed: true` |
| 43 | `city\|1805860\|t` | untouched; `changed: false` |
| 44 | `federal\|t` | untouched — placeless, no geoid segment |
| 45 | `county\|\|t` with no county slice | untouched, **not deleted** |
| 46 | both `city\|\|t` (newer) and `city\|1805860\|t` (older) | the newer survives at the bound key; one entry, not two |
