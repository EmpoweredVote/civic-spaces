- [ ] **Step 1: Create `src/types/explore.ts`**

```ts

 * Explore's record shapes. Neutral by design: this module imports nothing from
 * components/ or lib/, so src/mocks/civicSpacesExplore.ts and
 * src/components/explore/* can both depend on it without the import cycle that
 * existed while these lived in components/explore/exploreContent.ts.
 *
 * 🔴 ILLUSTRATIVE, NOT CIVIC RECORD applies to every record typed here. A topic
 * whose text was not drawn from a real source must carry provenance 'staff' and
 * must never claim otherwise. See the banner at the top of exploreContent.ts.
 */

/** The levels that have an Explore. Volunteer has none and is deliberately absent. */
export type ExploreLevel = 'federal' | 'state' | 'county' | 'city' | 'unified'

/**
 * Who put this topic here. Provenance is part of the record from day one because
 * the design admits three sources at once (staff, a local chapter, a government
 * body's own agenda) and the UI has to be able to say honestly which is which.
 */
export type TopicProvenance =
  | 'staff'                 // written at Empowered Vote. A conversation starter.
  | 'chapter'               // a nonpartisan local chapter (LWV, Braver Angels).
  | 'derived-from-agenda'   // built from a published agenda item. Verbatim title.
  | 'derived-from-vote'     // built from a published roll call.
  | 'member'                // requested by a member of this place.

/**
 * Was a closed union of eight literals. Now a string, because a bespoke,
 * agenda-derived or member-requested topic cannot be a member of a union that
 * ships with the app. Every lookup is therefore partial — see the note on
 * noUncheckedIndexedAccess in 16-SHARED.md.
 */

export interface ExploreTopic {
  id: TopicId
  category: string
  title: string
  summary: string
  /**
   * Optional since 16-01. An agenda item carries a title, a plain-language
   * summary and a stage; it does not carry a reason it matters, and writing one
   * for it would be inventing civic record.
   */
  whyItMatters?: string
  question: string
  /** Pre-filled, editable post title. Must fit createPostSchema (<=200). */
  suggestedTitle: string
  blurb?: string
  usesMeetingSources?: boolean

  // ── The slice dimension, new in Phase 16 ──────────────────────────────────

  /** Which level this topic belongs to. A local-scale topic must never show on Federal. */
  level: ExploreLevel
  /** The jurisdiction it is bespoke to; null means "applies anywhere at this level". */
  geoid: string | null
  provenance: TopicProvenance

  // ── Provenance detail, so the UI can show its working ─────────────────────

  /** e.g. "Ordinance 2026-22 · Second reading - final vote". Verbatim from the source. */
  sourceLabel?: string
  /** The published document this was derived from. Must pass isHttpUrl before rendering. */
  sourceUrl?: string
  sourceDate?: string
  /**
   * True when `summary` is a machine-written interpretation rather than the

  summaryIsGenerated?: boolean
```

- [ ] **Step 1: The key, and the draft key**

```ts
/**
 * Slice types with no place of their own.
 *
 * 🔴 These key on the slice type ALONE. The dev fixture gives federal the geoid
 * '3711' (a pre-taxonomy congressional district) and unified the empty string,
 * where production uses 'US' and 'UNIFIED'. Including the geoid would resolve a
 * different composition on localhost than in production — the exact class of bug
 * that only shows up after deploy.
 */
const PLACELESS = new Set(['federal', 'unified', 'volunteer'])

export function compositionKey(sliceType: string, geoid: string | null): string {
  return PLACELESS.has(sliceType) ? sliceType : `${sliceType}|${geoid ?? ''}`
}

export function draftKey(sliceType: string, geoid: string | null, topicId: TopicId): string {
  return `${compositionKey(sliceType, geoid)}|${topicId}`
}

export interface ParsedDraftKey {
  sliceType: string
  /** null for a placeless type, AND for a draft written signed out. */
  geoid: string | null
  topicId: TopicId
}

/** The reverse. Lives beside draftKey so the two formats cannot drift. */
export function parseDraftKey(key: string): ParsedDraftKey | null { /* null on anything unparseable */ }
```

🔴 `parseDraftKey` returns `null` rather than throwing. A corrupt `localStorage` value is a
thing that happens, and a throw here would take down `ExploreView`'s whole render.

Note the ambiguity `parseDraftKey` has to handle: a placeless key is
`federal|<topicId>` (two segments) while a place key is `city|<geoid>|<topicId>` (three) —
**and a signed-out place draft is `city||<topicId>`, also three, with an empty middle.** The
empty middle must parse to `geoid: null`, not to `geoid: ''`, or `canPostDraft` below will
compare `''` against a real geoid and refuse a draft it should accept.

- [ ] **Step 2: 🔴 `canPostDraft` — the anti-goal guard, as a pure function**

This is the check that stops a question written for one jurisdiction posting to another. It
must be **callable and checkable in isolation**, not buried in a `useCallback` where nothing
can reach it.

```ts
/**
 * May this draft be posted, and where?
 *
 * The anti-goal is a post landing in the wrong jurisdiction — a NATO question in
 * a city feed. A draft names its jurisdiction in its key, and the member must
 * still hold a slice of that type, with that geoid, right now.
 *
 * geoid === null has two sources and both are safe to accept:
 *   - a placeless type (federal, unified), which has no geoid to disagree about
 *   - a draft typed while signed OUT, which 16-04 re-keys to the member's own
 *     slice on sign-in. Until then it binds to whatever they hold for that type,
 *     which is today's behaviour and what 16-CONTEXT settled.
 */
export function canPostDraft(
  key: string,
  slices: Partial<Record<string, { id: string; geoid: string } | undefined>>,
): { ok: true; sliceType: string; sliceId: string } | { ok: false; reason: 'unparseable' | 'no-slice' | 'moved' } {
  const parsed = parseDraftKey(key)
  if (!parsed) return { ok: false, reason: 'unparseable' }
  const slice = slices[parsed.sliceType]
  if (!slice) return { ok: false, reason: 'no-slice' }
  if (parsed.geoid !== null && parsed.geoid !== slice.geoid) return { ok: false, reason: 'moved' }
  return { ok: true, sliceType: parsed.sliceType, sliceId: slice.id }
}
```

Returning a reason rather than a boolean matters: `no-slice` and `moved` are different
things to a member, and 16-04 decides what each one says.

- [ ] **Step 4: 🔴 `selectForModules` — pick featured and questions against the module list**

The naive version (`featured = topics[0]`, `questions = topics.slice(1, 5)`) has two bugs,
and both produce wrong pages rather than errors:

1. **On a composition with no `featured` module, `topics[0]` is never rendered at all** —
   and after Compass ranking, `topics[0]` is the single most relevant topic to that member.
2. **A topic owned by a dedicated module appears two or three times.** For Bloomington,
   `topics` is `[...agendaItems, ...generic]`, so the same ordinance shows as the featured
   card, as a question card, and in the Agenda section.

The rule: **a topic appears in exactly one module.**

```ts
/**
 * Assigns topics to the modules that will render them, so nothing is shown twice
 * and nothing with a module to live in is dropped.
 *
 * Order of claim:
 *   1. A module that OWNS a provenance claims those topics. 'agenda' owns every
 *      'derived-from-agenda' topic, because the agenda section renders the whole
 *      set with its own header and source link.
 *   2. 'featured' takes the first remaining topic — but only if the composition
 *      HAS a featured module.
 *   3. 'questions' takes the next few remaining.
 */
export function selectForModules(
  topics: ExploreTopic[],
  modules: readonly ModuleId[],
  questionCount = 4,
): { featuredTopicId: TopicId | null; questionTopicIds: TopicId[] }
```

Keep `questionCount` a parameter with a default so Task 5 can check the boundaries without
depending on the number.

- [ ] **Step 5: The Compass filter and the ranking**

`topicsForLevel(topics, level, compassLevelFlags?)` — filters to `topic.level === level`,
then drops a topic whose `compassTopicId` is flagged as not applying at this level.

🔴 **Exclusion only.** 45 of 60 Compass topics are flagged for all three levels, so the flags
cannot pick out "what federal leaders attend to"; what they *can* do is keep the six
local-only topics off Federal. A topic with no `compassTopicId`, or a catalog that did not
load, passes through — refusing to show a topic because a side lookup failed is worse than
showing it.

`rankByCompass(topics, answeredTopicIds)` — orders by whether the member has answered the
matching Compass topic.

```ts
/**
 * Below this, the ordering says nothing and source order is kept instead of
 * pretending to a signal. MIN_SPOKES in useCompassData.ts:14 is the precedent
 * for refusing to draw a conclusion from too little.
 */
export const MIN_RANKED = 3
```

Three properties the implementation must have, all checked in Task 5:

- **Stable.** Ties keep source order, so a reload never reshuffles the page.
- **A permutation.** It reorders; it never adds or removes. If a topic can vanish when
  Compass loads, the level filter has leaked into the ranking path.
- **Inert below `MIN_RANKED`.** Returns the input unchanged, same order.

Decision 7 is deliberate and load-bearing: Compass **ranks** topics using the **viewing
member's own** answers; it does not produce them, and no slice-wide aggregate of members'
political answers is computed anywhere.

- [ ] **Step 6: `resolveComposition`**

The design's resolution order: bespoke topics for this exact key; else the generic topics for
this level, level-filtered and Compass-ranked; and the seed slot, loud when bespoke is empty.
No geoid — a signed-out visitor, or a member with no slice for this tab — means generic only,
with no bespoke layer and no seed invitation: neither can seed a place the app cannot name.

```ts
topics      = bespoke.length > 0 ? [...bespoke, ...ranked] : ranked
modules     = DEFAULT_MODULES[level]
isUnseeded  = !!geoid && bespoke.length === 0
...selectForModules(topics, modules)
```

Build the module array; **do not mutate `DEFAULT_MODULES`**, which is a module-level constant
shared by every resolution (16-08 reorders it per composition and this is how that stays
safe).

- [ ] **Step 7: 🔴 `racesAreaFor` — and it returns null rather than falling back to a state**

```ts
/**
 * The area to ask for RACES — the member's most local place. City, else county,
 * else NOTHING.
 *
 * 🔴 There is deliberately no state fallback. A state-area query is wrong in both
 * directions at once, verified live 2026-10-24:
 *   - Indiana's state area returns all 9 US House districts; the member has one.
 *     Bloomington's city area returns District 9 alone.
 *   - A state area OMITS statewide races: North Carolina's has no US Senate race,
 *     California's has no Governor. Their city areas have both.
 *   - Federal geoid 'US' returns HTTP 500; 'UNIFIED' is not a place.
 *   - California's state area is 456 KB / 493 races against 17-50 KB for a city.
 * Falling back to the state would reintroduce the nine-House-races bug this
 * function exists to prevent. A member with no city or county slice gets no races
 * module, which is the honest answer — nine races a member cannot choose between
 * is worse than none.
 *
 * NOT electionAreaFor() from useNextElection.ts, which DOES fall back to the
 * state. That is correct for "when is the next election" (every area answered
 * 2026-11-03) and wrong for "which races are mine". Keep both; never merge them.
 */
const RACE_MTFCC = { city: 'G4110', county: 'G4020' } as const

export function racesAreaFor(slices): ElectionArea | null {
  for (const type of ['city', 'county'] as const) {
    const geoid = slices[type]?.geoid
    if (geoid) return { geoid, mtfcc: RACE_MTFCC[type] }
  }
  return null
}
```

- [ ] **Step 8: `isHttpUrl`**
