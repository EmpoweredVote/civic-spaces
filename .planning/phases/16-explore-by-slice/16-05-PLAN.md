# Phase 16-05 — The sibling-shard read-only gate

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On a sibling shard of the member's own jurisdiction, Explore offers **no** write —
not a button, not a textarea, and not the effect that reaches the composer without a button.

**Architecture:** `isViewOnly` already exists in `AppShell` and already reaches the feed and
the thread. This plan carries the same value into `ExploreCtx`, so every module inherits one
gate rather than each remembering its own, and adds the two things Explore specifically
needs: a notice with a **"Switch back to your community"** control (the shard selector lives
in the Conversations toolbar and is not reachable from Explore at all), and a refusal in
`handleStartConversation` so no programmatic path can slip past the UI. Then a committed
Playwright script that drives the real page and fails if any of it regresses.

🔴 **Why this is its own plan with its own verification.** `CLAUDE.md` records that this repo
shipped exactly half of this kind of gate once already — the feed was gated and the thread
was not. The write surface here is larger than "the Join button": **three** code paths reach
the composer, one of them with no button press at all, and **six** more controls write
drafts. Research Finding 5 enumerates all ten. A gate that covers nine of them is the same
failure in a new place.

🔴 **And the check must be able to see all ten.** The dev fixture shards **only Federal**
(`MOCK_SIBLINGS`, `devMockData.ts:255-258`), and `DEFAULT_MODULES.federal` has no `imagine`
and no `nearby` — so a script that only ever drives Federal can never observe affordances #2
and #6, and "no textarea found" would be true because there was never a textarea there.
Task 2 adds a City sibling so the check runs where the controls actually are.

**Tech Stack:** React 19 · TypeScript 5.7 · Vite 6 · Tailwind v4 · Playwright (**a global
install — not in `node_modules`**) · no test framework (see `16-SHARED.md`).

**Spec:** `16-DESIGN.md` (decision 5 — *"this is the third half of the landmine already

### Task 4: The programmatic path, and the race nobody can see

Affordance #3, plus the refusal behind all three.

🔴 **State the reachability honestly first.** `viewingSlices` is plain `useState` and is not
persisted, so a page load always starts with view-only `false`. The resume effect fires once
per mount (`resumedRef`, `ExploreView.tsx:144`), as soon as `isAuthenticated` and
`destination` resolve. The only way view-only can become true on a fresh load is a
`/post/<siblingPostId>` deep link — and the load-bearing fact there is that `openPost` calls
`setViewingSlices` **only after `await locatePost(...)`** (`AppShell.tsx:564-578`), so
view-only always lands in a **later commit** than the first render. That is true regardless
of effect ordering; the child-before-parent rule reinforces it but is not what the argument
rests on.

So on a fresh page load, the resume effect fires before view-only is set.

Two honest qualifications, neither harmful:

- **"Cannot coexist on any path" would be too strong.** `ExploreView` unmounts on the
  Volunteer tab (`hasExplore`, `AppShell.tsx:1045`) and remounts on return with
  `viewingSlices` **intact** — so a member who is view-only on City, visits Volunteer, and
  comes back gets a fresh mount with view-only already true. A marker surviving that window
  is unlikely but not impossible, which is precisely why `'defer'` exists rather than an
  assertion that the case is unreachable.
- The deep-link path is a **race**, not an ordering guarantee. Treat it as one.

That means this gate is defence in depth, not a currently-reachable bug — and saying so is
the point. What *is* reachable, and what Task 6 checks, is the invariant that falls out:
`handleStartConversation` resets `viewingSlices[tab]` to the member's own shard at
`AppShell.tsx:690` **before** calling `compose()`, so even in the race the composer opens on
the member's own shard and no RLS-rejectable write is attempted. The failure to guard against
is a future change that removes `:690` or reorders those effects.

**Files:**
- Modify: `src/lib/exploreComposition.ts` — `shouldResume`
- Modify: `src/components/explore/ExploreView.tsx:121-128, 145-163`
- Modify: `src/components/AppShell.tsx` — `handleStartConversation` (`:668-711`)

- [ ] **Step 1: Extract the resume decision into a pure function**

A browser cannot reach this decision reliably, so make it reachable to `node`:

```ts
/**
 * What to do with a "post this after sign-in" marker. Pure, so it can be checked
 * without a browser — the browser cannot reliably reach the view-only case (see
 * the note in 16-05 Task 4).
 *
 * - 'resume'          call startConversation, clear the marker
 * - 'drop-stale'      older than RESUME_MAX_AGE_MS, or no draft: clear, do nothing
 * - 'drop-unpostable' canPostDraft refused: clear the marker, KEEP the draft
 * - 'defer'           view-only, or no destination yet: leave the marker alone
 * - 'none'            no marker
 */
export function shouldResume(input: {
  marker: { sliceType: string; geoid: string | null; topicId: string; at: number } | null
  draft: { updatedAt: number } | undefined
  now: number
  maxAgeMs: number
  isViewOnly: boolean
  hasDestination: boolean
  postVerdict: { ok: boolean }
}): 'resume' | 'drop-stale' | 'drop-unpostable' | 'defer' | 'none'
```

🔴 `isViewOnly` yields **`'defer'`, not `'drop-stale'`**. The member asked to post this and
is merely reading someone else's shard; dropping their marker would lose that intent. Leave
it; it fires when they switch back, which is a real path.

- [ ] **Step 2: Use it in the effect**

`ExploreView.tsx:145-163` becomes a call to `shouldResume` and a `switch`. Two things the
effect must get right, and both are the difference between `'defer'` meaning "later" and
`'defer'` meaning "never":

- **Do not set `resumedRef` on `'defer'`.** Deferring once would otherwise be permanent.
- 🔴 **Put `isViewOnly` in the dependency array.** The effect currently depends on
  `[isAuthenticated, destination, startConversation]` (`:163`). A deferred marker has to be
  re-evaluated when the member presses Switch back, and that transition changes **only**
  `isViewOnly` — `destination` and `isAuthenticated` are unchanged, so without the new
  dependency React never re-runs the effect and the marker sits there until the next mount.

- [ ] **Step 3: Gate `startConversation` too**

All three paths funnel through `ctx.startConversation`. Make it a no-op while view-only
**and** keep every caller hidden (Task 5) — belt and braces, because the no-op alone leaves a
button that does nothing, which is its own kind of lie.

- [ ] **Step 4: The refusal at the far end**

Keep `AppShell.tsx:690`'s reset as the backstop and add a refusal in front of it:

```ts
// Defence in depth. Explore must not OFFER this while view-only (decision 5) and
// RLS would reject it anyway; a stale closure or a future reordering of the
// route and resume effects must not be the one path that gets through.
if (activeIsViewOnly) return
```

`SliceFeedPanel.handleCompose` (`:115-130`) checks only `is_suspended` and the `inform` tier
— it does **not** check `isViewOnly`. That is unchanged and fine, because the composer is
never mounted on a sibling shard; this refusal is what guarantees it is never asked to be.

- [ ] **Step 5: Add the checks**

In `scripts/check-composition.mjs`:

| # | Check | Expected |
|---|---|---|
| 48 | no marker | `'none'` |
| 49 | fresh marker, draft present, postable, not view-only, destination | `'resume'` |
| 50 | marker older than `maxAgeMs` | `'drop-stale'` |
| 51 | marker present, **no** draft | `'drop-stale'` |
| 52 | 🔴 view-only, everything else valid | `'defer'` — not dropped |
| 53 | no destination yet | `'defer'` |
| 54 | `postVerdict.ok === false` | `'drop-unpostable'` |
| 55 | view-only **and** stale | 🔴 **`'drop-stale'`.** Check staleness **before** view-only. A marker older than 24 h was abandoned, and keeping it alive because the member happens to be reading a sibling would park stale state indefinitely — a deferred marker is only re-evaluated on switch-back or a remount, so it could outlive the draft it points at. Staleness wins; implement the branches in that order. |

## Out of Scope

- **Changing RLS, or any migration.** The database is already correct: sibling reads are
  permitted, every write path is closed, and `slice_members` has no INSERT/UPDATE/DELETE
  policy at all. This plan only stops the UI offering what the database would refuse.
- **The suspended-member and `inform`-tier gates.** They live in
  `SliceFeedPanel.handleCompose` (`:115-130`), they are unchanged, and Explore's Join stays
  enabled for both. **Settled by Chris, 2026-10-25: the goal is RLS-scoped only**, so these
  are out of scope rather than undecided. A tier check is not an RLS rejection, and PR #112
  already judged the `inform` behaviour acceptable because the draft survives an upgrade.
- **Gating "Save on this device" or the Imagine / adventure / topic selections.**
  `16-CONTEXT.md` settled this: device-local preferences that never touch Supabase are not
  writes and stay. Removing them would make a sibling's Explore a dead page.
- **The shard selector itself.** It stays in the Conversations toolbar
  (`AppShell.tsx:968-982`). Explore gets a way *back*, not a second switcher.
- **Persisting `viewingSlices`.** It would make the resume race reachable and is a change to
  shell behaviour nobody asked for.
- **The four-way visual pass** on the notice. 16-10.
- Adding a frontend test framework.
