# Phase 16-07 — Races, debates and Compass ranking, from the member's *most local* area

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Surface the races already sitting unread in the elections response — the member's
*own* races, not their state's nine — plus the recorded debates and candidate forums that
join to them, and let Compass order the generic topics.

**Architecture:** The elections response has carried `races[]` and `candidates[]` all along;
`ElectionRecord` (`useNextElection.ts:27-33`) reads four fields of it and the type comment
says *"Races and candidates are ignored here"*. Widening that type is additive and does not
disturb `pickNextElection`. The work is in three pure functions and one join: pick the right
**area** (`racesAreaFor`, already built in 16-01), classify each race to a level **by its
name rather than by `district_type`**, drop withdrawn candidates, merge across the two or
three elections an area can return, and join `race_id` to the `raceIds` on published debate
and forum recordings. Compass is hoisted into `AppShell` for the first time and feeds the
ranking function 16-01 already shipped.

🔴 **The single most important line in this plan:** never ask the elections endpoint about a
state when you want races, and never ask it about `US` or `UNIFIED` at all.

**Tech Stack:** React 19 · TypeScript 5.7 · Vite 6 · TanStack Query · no test framework (see `16-SHARED.md`).

**Spec:** `16-DESIGN.md` (decision 8, and the "What actually serves decision 10" table rows
for races and debates), `16-CONTEXT.md` (the races and debates corrections; locked decision
7), `16-RESEARCH.md` **Finding 1**, **Finding 2 → Debates and forums**, Contradictions 4, 5
and 8, Pitfalls 2, 9 and 10 — read Finding 1 before Task 1.

**Depends on:** 16-06. **Execute serially after it** — see the plan-set table in 16-01.
Logically it needs 16-02 (the registry declares `races` and `debates` rooms) and 16-04 (Explore
follows the tab).

**Carries:** CONTEXT scope fence "surfacing the races already present in the elections
response"; CONTEXT corrections on races and on debate recordings; locked decision 7; DESIGN
decision 8 (the reachable half); research Contradictions 4, 5, 8; Pitfalls 2, 9, 10.

### Task 1: Widen the election type and query the right area

**Files:**
- Modify: `src/hooks/useNextElection.ts:26-33` (`ElectionRecord`), `:101-110`
  (`useElectionsQuery` — export it), and a new `useRacesForArea`
- Reference (do not edit): `:41-53` `electionAreaFor` — the function this must **not** be
  confused with; `src/lib/exploreComposition.ts` — `racesAreaFor` from 16-01

**Interfaces:**
- Consumes: `racesAreaFor` (16-01).
- Produces: widened `ElectionRecord`, `RaceRecord`, `CandidateRecord`,
  `useRacesForArea(area, userId): { races: RaceRecord[] | undefined; isLoading: boolean }`

- [ ] **Step 1: Extend the record, additively**

`ElectionRecord`'s comment says *"Races and candidates are ignored here"*. Replace it with
the truth and add the two fields. It is a **subset of the response, not a contract**, so
adding to it changes nothing about `pickNextElection` (`:76-81`) or the banner.

```ts
export interface CandidateRecord {
  candidate_id: string
  full_name: string
  photo_url: string | null
  is_incumbent: boolean
  /** 🔴 'active' | 'withdrawn'. The LIST route does not filter; we must. */
  candidate_status: string
  is_write_in: boolean
  politician_id: string | null
}

export interface RaceRecord {
  race_id: string
  position_name: string
  seats: number
  /** 🔴 Unreliable for statewide offices — see lib/races.ts. Never classify on it alone. */
  district_type: string | null
  candidates: CandidateRecord[]
}

export interface ElectionRecord {
  election_id: string
  election_name: string
  election_date: string
  election_type: string
  /**
   * 🔴 OPTIONAL, both of them, and deliberately so.
   *
   * MOCK_ELECTIONS (devMockData.ts:772) is the offline fallback for the dev id
   * and carries neither — it was written when this type was four fields. A
   * required `races` would make the fixture a type error, and the only ways to
   * fix that are to delete the fallback or to write candidate names into it.
   * The second is inventing civic record: a fixture full of plausible candidates
   * for real offices is exactly the thing the anti-goal forbids, and it would be
   * the first thing anyone reaches for to get a green build.
   *
   * Optional also matches the wire: this type is a subset of the response, and a
   * future route that omits races must degrade to an empty module, not a crash.
   */
  jurisdiction_level?: string
  races?: RaceRecord[]
}
```

Every consumer therefore treats `races` as possibly absent: `racesForLevel` takes
`elections.flatMap(e => e.races ?? [])`, and the module's `available` is false when the list
is empty. Do **not** add races to `MOCK_ELECTIONS` — the dev id reaches the live elections
API through the `/api` proxy and gets real races; the fixture is the offline fallback only.

`primary_party` and `result` are `null` on every row today; leave them off the type rather
than typing a field nothing may render.

- [ ] **Step 2: Export the shared query and add `useRacesForArea`**

`useElectionsQuery` (`:102`) is already keyed `['next-election', area?.geoid, area?.mtfcc, userId]`.
Export it and build `useRacesForArea` on top. Two consequences worth knowing:

- On the **City** tab, `racesAreaFor` and `electionAreaFor` resolve to the same area, so the
  races query is a **cache hit** on the one the banner and the events widget already made.
- On the **Federal** and **State** tabs they differ — `electionAreaFor` falls back to the
  state (right for "when is the next election"; every area answered `2026-11-03`), while
  `racesAreaFor` goes local. That is **one extra request per member**, deliberately, and it
  is the whole correctness fix.

Add a comment at `electionAreaFor` pointing at `racesAreaFor` and saying which is for what.
These two functions differ by one fallback and will otherwise be merged by someone being
tidy, which would silently reintroduce the nine-House-races bug.

Run: `npm run build` — exits 0; the banner and the events widget are unchanged.

### Task 2: Classify races without trusting `district_type`

**Files:**
- Create: `src/lib/races.ts`

**Interfaces:**
- Consumes: `ElectionRecord`, `RaceRecord`.
- Produces: `RaceLevel`, `MemberRace`, `racesForLevel(elections, level): MemberRace[]`

- [ ] **Step 1: Write it**

Four jobs, in order:

1. **Merge across elections.** LA's city area returns two; flatten
   `elections.flatMap(e => e.races)`, carrying each race's election name and date.
2. **Drop withdrawn candidates** (`candidate_status !== 'active'`), and drop a race left with
   none.
3. **Classify** to `'federal' | 'state' | 'other'`, from `position_name` first:
   - federal: `U.S. Senate`, `U.S. House` / `U.S. Representative`, `United States Senator` —
     match generously on the US-office prefixes, case-insensitively.
   - state: `Governor`, `Lieutenant Governor`, `Attorney General`, `Secretary of State`,
     `Treasurer`, `Comptroller` / `Auditor`, `Superintendent`, and `State Senate` /
     `State House` / `State Assembly` / `State Representative`.
   - everything else: `'other'`.
   Use `district_type` only as a **tiebreak**, never as the primary signal:
   `Comptroller (Auditor of State)` and `Treasurer of State` arrive as `LOCAL` while
   `Secretary of State` arrives as `STATE_EXEC`, verified live.
4. 🔴 **An unclassified race goes to `'other'` and is shown on neither tab.** Showing a race
   on the wrong level is the exact mismatch this phase exists to remove, and a heuristic over
   free text *will* meet a name nobody anticipated. Silence is the correct failure.

Sort within a level: federal — Senate before House; state — statewide executives before the
legislature. Keep it stable.

vanishes when Compass loads, the level filter has leaked into the ranking path.
