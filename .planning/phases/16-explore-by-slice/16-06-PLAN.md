# Phase 16-06 — Bloomington end to end: agenda-derived topics and the dev fixture override

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One real jurisdiction whose Explore is bespoke because its own city council wrote
it — proving the bespoke layer works end to end, with nobody at Empowered Vote authoring a
word about a place they have never lived.

**Architecture:** A public route this app does not call today,
`GET /api/meetings/:id/agenda-items`, returns structured items with verbatim titles,
legislation references, stages, source links and plain-language summaries. A new hook finds
Bloomington's **most recent** agenda (not the next one — more on that below) and fetches its
items; a pure function maps the ordinance and resolution items to `ExploreTopic`s with
provenance `derived-from-agenda`; `exploreData.ts` feeds them in as the bespoke layer for
`city|1805860`. A dev-only `?dev=1&place=bloomington` override repoints the fixture slices so
all of this is visible on localhost without a pasted token.

🔴 **The one city with real agenda coverage is Bloomington, not Los Angeles.** The example
the design used for "bespoke" is the one that cannot be bespoke yet, and Asheville — the dev
fixture city — has **zero** meetings. That inversion is why this plan exists in the shape it
does.

**Tech Stack:** React 19 · TypeScript 5.7 · Vite 6 (the `/api` dev proxy) · TanStack Query ·
no test framework (see `16-SHARED.md`).

**Spec:** `16-DESIGN.md` (decision 10, and the "What actually serves decision 10" table),
`16-CONTEXT.md` ("Settled after research" item 1; the agenda correction),
`16-RESEARCH.md` **Finding 2** and **Pattern 3** — read Finding 2 before Task 2; it has the
field list, the coverage, and the three fields that are not trustworthy.

**Depends on:** 16-05. **Execute serially after it** — see the plan-set table in 16-01.
Logically it needs 16-02 (the registry declares an `agenda` room) and 16-04 (Explore follows
the tab, so the City tab is where this lands).

`MOCK_CITY_SIBLING_ID`, its posts and its `MOCK_SIBLINGS` / `MOCK_FEEDS` entries so the

## What the source actually gives us

Verified live 2026-10-24 (`16-RESEARCH.md` Finding 2). Read this table before writing code;
three rows change what the derivation may do.

| Field | Reality | Consequence |
|---|---|---|
| `titleRaw` | **Verbatim agenda title.** The migration comment says "preserved for provenance". | Render as-is. Never paraphrase, never truncate in the data layer. |
| `legislationRef` | e.g. `Ordinance 2026-22`. "Extracted from the agenda, never invented." ~6–8 items per meeting. | Verbatim. Use it as the topic's chip and in the templated question. |
| `stage` | e.g. `First reading`, `Second reading - final vote`. "Adapter-encoded body rules, never LLM-inferred." | Verbatim. A useful chip. |
| `summaryPlain` | Plain-language text on only 5–10 of 15–24 items. The migration header calls it a "plain-language interpretation" — **written by the pipeline, not quoted from the agenda**. | 🔴 Set `summaryIsGenerated: true` and **say so in the UI**. Pitfall 4: `summaryPlain` reads authoritatively, and presenting generated text as the record is the quietest form of the invented-civic-record anti-goal. |
| `kind` | Closed vocabulary (CHECK-constrained): `ordinance`, `resolution`, `appointment`, `report`, `procedural`, `minutes`, `public-comment`, `proclamation`, `other`. | Filter to `ordinance` and `resolution`. The rest are not discussable topics. |
| `status` / `outcome` | 🔴 **Not reliable.** The 2026-10-14 meeting is in the past and all 24 items still read `status: upcoming, outcome: null`; the 2026-09-02 meeting has 5 `passed` outcomes while still `status: upcoming`. | **Never gate on `status`.** Do not render `outcome` either. |
| `sourceUrl` | `https://bloomington.in.gov/onboard/meetingFiles/<n>/download` — the agenda file. | Link it, through `isHttpUrl`. |
| The meetings *list* | 27 fields, **no agenda items**. Items are a separate public route. | Two requests, not one. |
| Coverage | **4 scheduled Bloomington rows**: 2026-08-05, 09-02, 09-16, 10-14. **Asheville: 0. Los Angeles: 0 council rows.** | Bloomington is the only proof available. |
| "Upcoming" | 🔴 `useUpcomingMeetings` keeps only future meetings and **returns zero rows today** — the newest scheduled meeting is ten days old. It will be empty roughly half the time. | **Derive from the most recent agenda, not the next one.** Do not reuse `useUpcomingMeetings` for this. |
| `state` | Populated on the `scheduled` rows; mostly `null` on published ones. | Query `city` + `state` + `status=scheduled`, which is the combination that works. |

Real items from the latest agenda, as examples of what a derived topic carries:
`Ordinance 2026-22` (automated licence plate readers; second reading, final vote),
`Appropriation Ordinance 2026-02` (2027 budget and tax rates), `Ordinance 2026-30` (general
obligation bonds), `Resolution 2026-22` (ADA transition plan), `Ordinance 2026-21`

### Task 2: Fetch the most recent agenda

**Files:**
- Create: `src/hooks/useAgendaItems.ts`
- Reference (do not edit): `src/hooks/useUpcomingMeetings.ts` — the shape to match, and the
  filter to **not** reuse (`:43-45`); `src/lib/evApi.ts` — `EV_API_ORIGIN`

**Interfaces:**
- Consumes: `EV_API_ORIGIN`.
- Produces: `AgendaItem`, `AgendaSource`,
  `useAgendaItems(city, stateAbbrev): { agenda: { meeting: AgendaSource; items: AgendaItem[] } | undefined; isLoading: boolean }`

- [ ] **Step 1: Write the hook**

Two requests, both public and unauthenticated, both through the `/api` proxy in dev:

```ts
// 1. The city's scheduled meetings. NOT useUpcomingMeetings: that hook keeps only
//    meetings still in the future, and it returns zero rows today — the newest
//    scheduled Bloomington meeting is 2026-10-14. An agenda that has already been
//    heard is still the best description of what this council is working on, and
//    it is what exists roughly half the time.
`${EV_API_ORIGIN}/api/meetings?city=${city}&state=${state}&status=scheduled`

// 2. The items of the most recent one.
`${EV_API_ORIGIN}/api/meetings/${latest.id}/agenda-items`
```

Sort the meetings by `date` descending and take the first. Apply a **freshness window** —
45 days — and return `undefined` beyond it rather than presenting a stale agenda as current:
a three-month-old agenda is not what the council is working on.

`enabled: !!city && !!state`, a long `staleTime` (an agenda does not change hour to hour),
`retry: 1` — matching `useUpcomingMeetings:65-71`. Key on `['agenda-items', city, state]`.

Type `AgendaItem` with the fields the derivation uses: `id`, `itemNumber`, `titleRaw`,
`kind`, `legislationRef`, `summaryPlain`, `stage`, `sourceUrl`. Deliberately **omit**
`status` and `outcome` from the type — they are unreliable (see the table above), and the
cheapest way to guarantee nothing gates on them is for them not to exist downstream.

### Task 3: Derive topics without writing a word of civic content

The careful part. Pure, so it can be run against the saved response.

- [ ] **Step 1: Write the mapping**

| `ExploreTopic` field | Value | Source |
|---|---|---|
| `id` | `agenda-${item.id}` | stable and unique across agendas |
| `title` | `item.titleRaw` | **verbatim** |
| `summary` | `item.summaryPlain` | machine-written → see `summaryIsGenerated` |
| `whyItMatters` | **omitted** | not derivable; writing one would be inventing |
| `category` | from `item.kind` — "On the council agenda" | our words, no fact |
| `question` | templated from `legislationRef`, e.g. *"What would you want to know about Ordinance 2026-22?"* | template text states nothing |
| `suggestedTitle` | templated, **≤200 chars** (`createPostSchema`) — truncate the template, never the reference | ditto |
| `level` / `geoid` | the slice's | bespoke by construction |
| `provenance` | `'derived-from-agenda'` | |
| `sourceLabel` | `legislationRef` + `stage`, joined — both verbatim | |
| `sourceUrl` | `item.sourceUrl` when `isHttpUrl` passes, else omitted | ASVS V5 |
| `sourceDate` | the meeting's `date` | |
| `summaryIsGenerated` | `true`, always | 🔴 non-negotiable |

Filter: `(kind === 'ordinance' || kind === 'resolution')` **and** a non-empty
`summaryPlain`. An item with no summary has nothing to discuss from, and the rule above
forbids writing one.

Never read `status` or `outcome`. Never sort by them. Cap at a sensible number (6–8) so one
budget meeting does not become a wall, keeping agenda order (`position`).

- [ ] **Step 1: Feed the bespoke layer through the seam**

`useExploreComposition` gains optional `city` and `stateAbbrev` inputs and, inside
`exploreData.ts`, calls `useAgendaItems` + `agendaItemsToTopics` to produce the `bespoke`
array that 16-01's `resolveComposition` already accepts. Explore content continues to enter
through exactly one file.

When the real `GET /api/civic-spaces/explore?sliceType=&geoid=` route lands (see the handoff
in 16-09), this collapses: the route returns the composition with its bespoke topics already
in it, and the two client-side requests and `agendaTopics.ts` are deleted. Say so in a
comment, so the next person knows this is a stepping stone and not the destination.

`ActiveExplore` already resolves the city name and the state abbreviation for
`useUpcomingMeetings` (`AppShell.tsx:330`) — pass the same two values in. No new lookup.

🔴 **Fetch by name; attach by geoid.** The meetings API only accepts a city *name* plus a
state abbreviation, so the request has to be made that way. The **attachment** must not be:
the name is not a key. Two cities with the same name in one state would collide (Research
Finding 2 flags this, low risk today only because one city is covered), and the composition
key is `(slice_type, geoid)` everywhere else in this phase.

So:

1. `agendaItemsToTopics` stamps each derived topic with the **slice's geoid** — the one the
   composition was resolved for, not anything taken from the response.
2. Before `resolveComposition` accepts the `bespoke` array, it drops any topic whose `geoid`
   does not equal the composition's own. 16-01's resolver already has both values; make the
   filter explicit rather than trusting the caller.

The result: a name collision yields topics that are discarded rather than topics attached to
the wrong city. Add two checks to `scripts/check-composition.mjs`:

| # | Check | Expected |
|---|---|---|
| 56 | `resolveComposition` for geoid B, given a bespoke topic stamped geoid A | the topic is discarded; `isUnseeded: true` |
| 57 | the same topic stamped geoid B | kept; `isUnseeded: false`; it leads `topics` |

`isUnseeded` otherwise falls out for free: a city with agenda coverage has bespoke topics, so
it is seeded; everywhere else is not. That flag is what 16-08 renders the invitation against.

- [ ] **Step 2: The module**

A section listing the derived topics, each a card in the existing question-card vocabulary:
the verbatim title, the `legislationRef` / `stage` chips, and the plain-language summary.

The section header carries the provenance for the whole set — *"From the {body}'s agenda of
{date}"* — with the agenda file linked through `isHttpUrl`. That is a real sentence about a
real document, and it is what makes the rest honest.

🔴 **Take the body's name from the meeting record. Do not write "City Council".**
Bloomington's body is the **Common Council**, and the live record says so: every one of its
four scheduled meetings is titled `Common Council Regular Session — YYYY-MM-DD` (verified
2026-10-24). "Bloomington City Council" is a plausible-sounding name for a body that does
not exist under that name, which is invented civic record in its mildest and most likely
form — and the next covered city will be a Board of Supervisors, a Metro Council or a City
Commission, none of which are a City Council either.

Derive it from the meeting's `title` (strip the trailing `meetingType` and the date) or fall
back to `meetingType`. If neither yields a usable name, write *"From the agenda of {date}"*
and link the document — naming no body is honest; naming the wrong one is not.

🔴 The generated-summary label must be visible without opening a topic. The title is the
council's; the summary is not; a reader who sees only the card must still be able to tell
them apart. `SourceNote` (16-02) already encodes this — use it here, do not re-word it.

Agenda titles run long (60–150 characters). Clamp in **CSS**, never in the data —
`line-clamp-3` with the full text in the topic detail. A truncated civic title stored as
data is a quote nobody said.

Registry: `available: (ctx) => ctx.agenda !== undefined && ctx.agenda.topics.length > 0`.
`emptyState` is a real reserved room, not `'hide'`: *"When your city publishes its council
agendas here, the items it is working on will appear in this space."* Coverage is one city
nationally, so **this empty state is what almost every member sees** — write it as a promise,
not an apology. Goal 6.

## Out of Scope

- **Los Angeles, and seeding any other place.** LA has zero council rows in the meetings API
  and no way to ask "what is LA council working on" — its votes are per council file
  (`/api/council-files/:fileNumber`), not listable by place. Seeding the rest is content work
  the design's non-goals defer.
- **County and state agendas.** No source. The `agenda` module is in the County composition
  and shows its reserved room there.
- **Roll-call votes on agenda items.** `GET /api/meetings/:id/votes` returns real tallies for
  *published* meetings and is empty for scheduled ones. Reachable, out of scope, and listed
  in 16-09's handoff as a thing we would use.
- **`GET /api/meetings/:id/summary`** (`executiveSummary`, `keyDecisions`, `sections`). Real
  and interesting; not needed to prove the bespoke layer.
- **Asking ev-accounts to widen coverage.** The pipeline runs where it runs. 16-09's handoff
  notes that coverage is the limiting factor; it does not ask for a city.
- **Ballot measures.** Not served anywhere. 16-09.
- Adding a frontend test framework.
